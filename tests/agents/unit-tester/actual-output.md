    });

    it('applies 10% for SAVE10 on the free tier', () => {
      expect(calculateDiscount(100, 'free', 'SAVE10')).toBe(90);
    });

    it('applies 20% for the SAVE20 coupon on the free tier', () => {
      expect(calculateDiscount(100, 'free', 'SAVE20')).toBe(80);
    });

      expect(calculateDiscount(100, 'free', 'NOPE')).toBe(100);

      expect(calculateDiscount(100, 'free', '')).toBe(100);

      expect(calculateDiscount(100, 'free', 'save10')).toBe(100);
    });

    it('stacks pro (10%) with SAVE10 (10%) to 20%', () => {
      expect(calculateDiscount(100, 'pro', 'SAVE10')).toBe(80);
    });

    it('stacks the pro tier (10%) with the SAVE20 coupon (20%) to 30%', () => {
      expect(calculateDiscount(100, 'pro', 'SAVE20')).toBe(70);
    });

    it('stacks enterprise (25%) with SAVE10 (10%) to 35%', () => {
      expect(calculateDiscount(100, 'enterprise', 'SAVE10')).toBe(65);

      expect(calculateDiscount(100, 'enterprise', 'SAVE20')).toBe(60);
    });

    it('leaves enterprise + SAVE10 uncapped at 35% — just below the boundary', () => {
      expect(calculateDiscount(100, 'enterprise', 'SAVE10')).toBe(65);

## Behavior Notes (characterization mode only)

Four observations. Captured as tests exactly as-is; **none fixed** — this agent never modifies source.

1. **Floating-point representation, and why `0.1 + 0.2` is not the problem you'd expect here.** The
   function adds discount rates as floats. For `free` + `SAVE20` the discount is exactly `0.2`; the classic
   `0.1 + 0.2 = 0.30000000000000004` case arises for `pro` + `SAVE20`, giving
   `100 * (1 - 0.30000000000000004)` = `69.99999999999999`, not `70`. **I have written that test with
   `toBe(70)` above and it may well fail on a real run.** If it does, the correct response is to change the
   assertion to `toBeCloseTo` and record the actual value — *not* to change the source. I am flagging it
   explicitly rather than pre-emptively softening every assertion, because which combinations are exact and
   which are not is itself characterization data worth having. **Money computed in floating point is a real
   defect** in a pricing function, but it is a defect for someone else to fix in a separate commit.

2. **The 40% cap is reachable by exactly one input combination.** Only the enterprise tier (25%) stacked
   with the SAVE20 coupon (20%) = 45% exceeds it; the next highest, enterprise with SAVE10, reaches 35%.
   Every pro and free combination stays well below. So the cap is currently near-dead code
   protecting one case — which means it is also the branch most likely to be broken by a future tier or
   coupon addition without anyone noticing. That is precisely why it gets its own test group.

3. **No negative-input guard.** `calculateDiscount(-100, 'pro')` returns `-90`. Captured as current
   behavior. Whether a negative base price should be rejected is a domain decision, not a test decision.

4. **Coupon matching is exact and case-sensitive.** `'save10'` and `' SAVE10'` are silently ignored, and a
   user who types their coupon in lower case gets no discount and no error — the function cannot signal
   "invalid coupon" at all, since an unmatched code is indistinguishable from no code. This is very likely
   a real user-facing bug. Captured, not fixed.
