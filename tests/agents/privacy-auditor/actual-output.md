# Privacy Audit Report: Payment Webhook Handler

## Summary
- Total Artifacts Audited: **1** (`implementation-notes.md`)
- Secret Leaks Found: **3** (one artifact occurrence, two source-code occurrences the artifact reports)
- PII Violations Found: **2** fields in one logging statement, plus an unbounded exposure surface behind them

**Overall: BLOCKER.** This feature must not merge in its current state. The PII logging is the more serious
of the two categories, and the reason is counterintuitive enough to state up front: the hardcoded key is a
Stripe *test* key, which is the finding that looks worse and matters less. Cardholder email and name written
to INFO logs is the finding that looks routine and is the actual violation.

## Findings

### Critical Secret Leaks

- [`.claude/feature-workspace/payment-webhook/implementation-notes.md`]: Contains a literal Stripe key,
  `sk_test_4eC39HqLyjWDarjtT1zdp7dc`, written out twice in the artifact body — once under "Stripe Test
  Credentials Used During Development" and once under "Environment Variables".

  **HIGH, not CRITICAL, and the distinction is deliberate**: the `sk_test_` prefix marks this as a Stripe
  test-mode key. It cannot move real money and cannot read live customer data. Grading it CRITICAL would be
  the easy call and the wrong one — an auditor that treats every key-shaped string as an emergency gets
  ignored on the run where the string starts with `sk_live_`.

  It is still a genuine finding for three reasons, and none of them are "it might be live":
  1. **The artifact is persisted.** Pipeline artifacts move from `.claude/feature-workspace/` to
     `docs/features/` and into git history. Once committed, the string is permanent regardless of how it is
     later edited.
  2. **Test keys are still credentials.** They grant access to a Stripe test account, its test customers,
     and its configuration.
  3. **This is the habit, not the incident.** A key hardcoded during development and documented in the notes
     is precisely the workflow that eventually commits a live key. The control that has failed here is not
     "which key" — it is "keys go in source and in artifacts", and that control fails identically for both
     kinds.

- [`src/config/stripe.config.ts`]: The artifact states `STRIPE_API_KEY` is **hardcoded** in this file as
  `sk_test_4eC39HqLyjWDarjtT1zdp7dc`. **BLOCKER** — a direct violation of
  `architecture-guardrails.md` #3 (never hardcode API keys, tokens, or connection strings; use `.env`
  placeholders mapped to a secure vault). *Source not independently inspected — the artifact reports it.*

- [`src/webhooks/stripe.handler.ts`]: The artifact states the same key was hardcoded here during
  development and **"not yet removed"**. **BLOCKER**, same guardrail. *Source not independently inspected.*

  Worth noting what is done **correctly**, since it shows the right pattern already exists in this codebase:
  `STRIPE_WEBHOOK_SECRET` is read from `process.env`. Two secrets, two different handling paths, in one
  feature. The correct path is already available and was simply not used for the API key.

### Privacy / PII Violations

- [`src/webhooks/stripe.handler.ts`]: `customer_email` and `customer_name` are extracted from the Stripe
  event payload and written to the application log at **INFO** level:

  ```typescript
  logger.info({ customer_email, customer_name, amount }, 'Payment succeeded');
  ```

  **BLOCKER — and this is the most serious finding in the audit**, above both secret findings.

  Email address and full name are personal data under GDPR and CCPA, and this logs them for **every
  successful payment**, at a level that is captured in every environment including production. The specific
  consequences:

  - **The blast radius is the log pipeline, not the application.** Logs are shipped to third-party
    aggregators, retained for months or years under retention policies written for debugging rather than for
    personal data, and are readable by a far broader group than the payments database — support, SRE, on-call
    engineers, and anyone with a dashboard login. This effectively creates a second, less-governed copy of
    the customer table.
  - **Deletion requests become unsatisfiable.** A GDPR erasure request can be honored in a database. It
    generally cannot be honored across log archives and their backups. Once this line runs in production,
    the organization holds personal data it cannot delete on request — and that is not a bug that can be
    fixed forward, only stopped from accumulating further.
  - **INFO is the wrong level even if the fields were acceptable.** INFO is retained everywhere and sampled
    nowhere; DEBUG at least would be off in production. But the level is a mitigation, not the fix.
  - **The purpose is stated as "for debugging."** Nothing in a payment-succeeded debugging workflow requires
    the customer's name. The Stripe event id and the internal order id identify the transaction completely
    and are not personal data.

  `amount` is **not** flagged. A monetary amount without an identity attached is not personal data, and it
  is genuinely useful for debugging.

- **Unbounded exposure risk behind the two named fields**: the handler receives the full Stripe event and
  destructures fields from it. Stripe payloads routinely also carry billing address, card last-four, and
  payment-method metadata. Today two fields are logged; the next "add one more field for debugging" edit is
  a one-line change with no control standing in its way. **The structural fix is a field allowlist**, not a
  removal of these two names — otherwise this finding recurs with different field names in three months.

## Recommendations
- [ ] **Remove `customer_email` and `customer_name` from the log line.** Replace with non-identifying
      correlation fields: `logger.info({ stripe_event_id, order_id, amount }, 'payment succeeded')`. This is
      the single highest-priority action in this report.
- [ ] **Add a field allowlist for anything derived from a Stripe event** before it can reach a log or a span
      attribute, so the raw event object cannot escape the handler. Fixes the class, not the instance.
- [ ] **Move `STRIPE_API_KEY` to `process.env`**, sourced from the secrets vault, with a placeholder in
      `.env.example`. The `STRIPE_WEBHOOK_SECRET` handling in this same feature is the pattern to copy.
- [ ] **Remove the hardcoded key from `src/webhooks/stripe.handler.ts`** — the artifact states it is still
      there.
- [ ] **Redact the key from `implementation-notes.md` before this artifact is persisted** to
      `docs/features/`. *Not performed by this agent — privacy-auditor reports, it never sanitizes or
      overwrites.*
- [ ] **Rotate the test key.** It appears in at least three places including a pipeline artifact bound for
      git history. Rotation is cheap for a test key and the right reflex to establish before the same
      situation arises with a live one.
- [ ] **For a human to consider**: two separate controls failed in one feature — a secret in source and PII
      in logs — and both are mechanically detectable. A pre-commit grep for `sk_live_`/`sk_test_` patterns,
      and a lint rule flagging `logger.*` calls whose arguments include identifiers matching
      `email|name|phone|address`, would catch this class at authoring time. Proposed for a human decision;
      both have false-positive cost and neither is this agent's to add.
- [ ] Nothing was modified. No artifact was edited, sanitized, or overwritten.
