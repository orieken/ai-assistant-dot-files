# Pattern Review Report: Site-Centric Architecture

## Summary
- Total Pattern Docs Audited: **1**
- Stale Paths Found: **1**
- Stale Code Snippets: **1**

Verdict: **STALE.** The document describes the Site-Centric pattern correctly at the conceptual level — the
`BaseSite` → `BasePage` → `BaseElement` → `BaseFlow` hierarchy and the rejection of the Page Object Model
are both current and correctly stated. What has rotted is everything concrete: one class was renamed two
minor versions ago, one file moved three, and both are still presented as current with line-number
precision.

That combination is the specific danger with pattern documents. Prose that is merely out of date reads as
out of date. A code snippet annotated `// From src/saturday-core/src/base/BasePage.ts (line 8)` reads as
*verified* — the line number is a claim of freshness — and a reader will trust it well past the point it
stopped being true.

## Findings

### Stale File Paths
- [`docs/patterns/site-centric.md`]: References `src/saturday-core/src/managers/SiteManager.ts` in the
  "SiteManager Multi-Context Pattern" section. **The file was moved to
  `src/saturday-core/src/orchestration/SiteManager.ts` in v2.0**, per the document's own trailing comment.

  The directory rename from `managers/` to `orchestration/` is not cosmetic — it is a signal that the
  framework reclassified what `SiteManager` *is*, from a manager-of-things to an orchestration component.
  The pattern document still frames it as a manager ("Use `SiteManager` to orchestrate cross-application
  journeys. Each application registers itself with the manager at initialization"), which straddles both
  vocabularies. Whether the prose needs updating too, or whether "manager" remains the right conceptual
  term, is a judgment for whoever owns the framework — flagged, not decided.

  **Also**: the `BaseSite` snippet's constructor takes `SiteManager` as a parameter, so the moved path
  invalidates the import a reader would need to write to use that snippet. The two findings compound.

### Stale Code / Schema Snippets
- [`docs/patterns/site-centric.md`]: The `BasePage` snippet is annotated
  `// From src/saturday-core/src/base/BasePage.ts (line 8)` and shows `export abstract class BasePage`.
  **The class was renamed to `AbstractPage` in v2.1**, per the document's own inline comment — so the
  snippet documents a class name that no longer exists.

  This is the more serious of the two findings, for three reasons:
  1. **`BasePage` is named in the Overview's hierarchy** (`BaseSite` → `BasePage` → `BaseElement` →
     `BaseFlow`) as well as in the snippet. The stale name appears at least twice and is load-bearing in the
     document's central diagram, so the fix is not a one-line snippet edit.
  2. **A renamed class fails loudly but confusingly.** A reader writing `extends BasePage` gets a compile
     error naming a symbol the documentation told them to use — the worst kind of documentation failure,
     because the reader's first assumption is that they have made a mistake, not that the doc has.
  3. **The document already knows.** Both stale facts are annotated in-line (`// This class was renamed to
     AbstractPage in v2.1 — snippet is stale`, `// File was moved to ... in v2.0`). Someone noticed the
     drift, recorded it beside the wrong content, and left the wrong content in place. That is a
     documentation process finding, not just a content one: a comment saying "this is stale" is a note to
     the next author, and it does nothing for the reader who copies the snippet above it.

- The `BaseSite` snippet is annotated `// From src/saturday-core/src/base/BaseSite.ts (line 12)` and carries
  **no** staleness annotation. It may well be current. But `BasePage` sits in the same `base/` directory and
  was renamed, so `base/BaseSite.ts` cannot be assumed correct by proximity — and the `line 12` claim
  in particular is the kind of detail that goes stale on any edit to the file above it, without anyone
  noticing. **Unverified in this run** (no source tree available); flagged for confirmation rather than
  reported as either PASS or STALE, since asserting either without checking would be the same error the
  document made.

### On line-number citations
A pattern-document-wide observation rather than a finding against a specific line: both snippets cite exact
line numbers. Line numbers are the fastest-decaying reference in any document — they break on any insertion
above them, silently, with no rename and no moved file to notice. If the citations exist to help a reader
find the source, a path plus a symbol name (`BaseSite` in `base/BaseSite.ts`) is nearly as useful and
survives ordinary editing. Worth raising with whoever maintains these docs; a convention change is cheaper
than repeatedly re-verifying line numbers that nothing checks.

## Recommendations
- [ ] **Rename `BasePage` to `AbstractPage` throughout** — the snippet, the Overview hierarchy, and any
      other prose reference. This is the finding a reader hits first and it fails at compile time.
- [ ] **Update the `SiteManager` path** to `src/saturday-core/src/orchestration/SiteManager.ts`, and decide
      whether the surrounding "manager" prose should follow the reclassification the v2.0 move implies.
- [ ] **Remove the two inline staleness comments once the content is fixed.** Leaving them alongside
      corrected content is worse than not having them — the next reader cannot tell whether the comment or
      the code is current.
- [ ] **Verify the `BaseSite` snippet and its `line 12` citation** against the current source. It is the
      only concrete claim in the document that has not been checked either way.
- [ ] **Consider dropping line-number citations** in favor of path-plus-symbol references, as a convention
      for these documents.
- [ ] **For a human**: both stale facts were known and annotated rather than fixed, and the drift spans two
      minor versions (v2.0 and v2.1) without either release updating this document. That is a release-process
      gap rather than an authoring one — a rename or a file move is exactly the change that should trigger a
      pattern-doc check, and a grep for referenced class names and paths during release would have caught
      both.
