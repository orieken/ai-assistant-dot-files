# Implementation Notes: User Avatar Upload

> **Context debt**: no `.claude/feature-workspace/user-avatar-upload/context-manifest.md` was present —

## Files Created
- `src/storage/storage-adapter.interface.ts` — the `StorageAdapter` port. Defined **first**, in the
  consumer's layer, so nothing above it ever imports `@aws-sdk/client-s3`. Three methods only: `put`,
  `remove`, `publicUrlFor`. No `list`, no `copy`, no presigned-URL method — YAGNI; the analysis requires
  none of them.
- `src/storage/s3-adapter.ts` — `S3StorageAdapter implements StorageAdapter`. The only file in the
  codebase that imports the AWS SDK. Owns bucket/region configuration, an explicit request timeout, and
  key construction. Wrapped by the framework's `CircuitBreaker`; no hand-rolled retry loop.
- `src/users/upload-handler.ts` — the use case. Validates the file, delegates persistence to
  `StorageAdapter`, updates the row, then deletes the previous object. Contains no AWS types.
- `src/users/avatar-file.ts` — `AvatarFile` value object: parses and validates the incoming buffer's size
  and content type once, at the boundary, and is un-constructible in an invalid state. This is what keeps
  the 2 MB limit and the format allowlist out of the handler as loose `if`s.
- `db/migrations/0031_add_avatar_url.sql` — **Expand phase only**: `ALTER TABLE users ADD COLUMN
  avatar_url TEXT` and `ADD COLUMN avatar_key TEXT`, both nullable, no default needed, no backfill. No
  `DROP`, no `RENAME`, no `NOT NULL` without `DEFAULT`. There is no Contract phase in this release.

## Files Modified
- `src/users/user-repository.ts` — added `updateAvatar(userId, { avatarUrl, avatarKey })`, which performs a
  **conditional update returning the previous key** in a single statement (see Key Decisions #2 — this is
  the concurrency fix, and it is the reason this method returns something instead of `void`).

## Interface Design

Written before any implementation, per Interface-First Design. If these could not be written without
peeking at an S3 call, the design would not have been ready.

```ts
// src/storage/storage-adapter.interface.ts — use-case layer, consumer-owned.
// Note: no AWS types, no Buffer-of-unknown-shape, no options bag "for later".
export interface StoredObject {
  readonly key: string;
  readonly url: string;
}

export interface StorageAdapter {
  put(key: string, body: Uint8Array, contentType: string): Promise<StoredObject>;
  remove(key: string): Promise<void>;
  publicUrlFor(key: string): string;
}
```

```ts
// src/users/avatar-file.ts — value object; primitive obsession stops here.
export type AvatarContentType = 'image/jpeg' | 'image/png';

export class AvatarFile {
  private constructor(
    readonly bytes: Uint8Array,
    readonly contentType: AvatarContentType,
    readonly extension: 'jpg' | 'png',
  ) {}

  /** Returns AvatarFile, or a typed rejection reason — never throws for user error. */
  static parse(bytes: Uint8Array, declaredType: string): AvatarFile | AvatarRejection;
}

export type AvatarRejection =
  | { reason: 'too_large'; maxBytes: number; actualBytes: number }
  | { reason: 'unsupported_format'; allowed: AvatarContentType[]; received: string };
```

```ts
// src/users/upload-handler.ts — use case.
export interface UploadAvatarResult {
  avatarUrl: string;
}

export class UploadAvatarHandler {
  constructor(
    private readonly storage: StorageAdapter,
    private readonly users: UserRepository,
    private readonly clock: Clock,
  ) {}

  execute(userId: UserId, file: AvatarFile): Promise<UploadAvatarResult>;
}
```

```ts
// src/users/user-repository.ts — added method.
export interface AvatarUpdate {
  avatarUrl: string;
  avatarKey: string;
}

export interface UserRepository {
  /**
   * Atomically sets the new avatar and returns the key it replaced (null if there
   * was none). Callers use the returned key to clean up the superseded object.
   */
  updateAvatar(userId: UserId, next: AvatarUpdate): Promise<{ replacedKey: string | null }>;
}
```

**Content-type note**: `AvatarFile.parse` does not trust the declared MIME type — it checks the leading
magic bytes (`FF D8 FF` for JPEG, `89 50 4E 47` for PNG) and requires them to agree with the declaration.
A `.png` header on a declared `image/jpeg`, or an SVG with an `image/png` label, is rejected. The analysis
said "unsupported format (GIF, SVG, etc.) returns 422"; taking the client's word for the format would have
satisfied the acceptance criterion in the happy case while leaving an SVG-upload hole open.

## Named Refactoring Log

- **Extract Class**: `src/users/upload-handler.ts:1` → `src/users/avatar-file.ts`
  - **Before**: the first green implementation validated size and format with two `if` statements inside
    `execute`, working on a raw `Buffer` and a raw `string` MIME type — primitive obsession, and the
    handler had two reasons to change (validation policy, upload orchestration).
  - **After**: `AvatarFile` value object owns parsing and validation; `execute` receives an already-valid
    file and cannot be called with an invalid one. Handler dropped from 26 to 11 lines.

- **Introduce Parameter Object**: `src/users/user-repository.ts:88`
  - **Before**: `updateAvatar(userId, avatarUrl, avatarKey)` — three parameters, two of which always
    travel together and are both strings (trivially swappable at a call site).
  - **After**: `updateAvatar(userId, next: AvatarUpdate)` — two parameters, and the two strings are now
    distinguishable by name at the type level.

- **Replace Nested Conditional with Guard Clauses**: `src/users/upload-handler.ts:19`
  - **Before**: the storage-failure and row-update paths were nested two deep inside a `try` with an
    `else` branch; complexity measured 6 and was one edge case away from breaching the < 7 budget.
  - **After**: early returns on each rejection path; nesting depth 1, complexity 3.

- **Separate Query from Modifier** *(deliberately NOT applied — logged because a reviewer will ask)*:
  `updateAvatar` both mutates the row and returns the replaced key. That is a knowing violation of the
  rule. The alternative — read-then-write — reintroduces the exact race the analysis flagged. Atomicity
  wins over purity here; see Key Decisions #2.

## Key Decisions

1. **`StorageAdapter` is defined in the consumer's layer, not alongside the S3 implementation.** The
   analysis says the SDK "must hide behind `StorageAdapter`". Defining the interface next to the adapter
   would technically satisfy that sentence while still pointing the dependency arrow outward. It lives in
   `src/storage/storage-adapter.interface.ts` with no AWS import, and the use case depends only on it.

2. **The concurrent-upload race is solved with a conditional UPDATE, not a read-then-write.** Two
   simultaneous uploads from one user both succeed at S3 (different timestamps, different keys), then race
   on the `users` row. Reading the old key and then writing loses one object to permanent orphanhood. So
   `updateAvatar` performs a single `UPDATE users SET avatar_url = $2, avatar_key = $3 WHERE id = $1
   RETURNING avatar_key AS replaced_key` — the RETURNING clause yields the value the row actually held at
   write time, so whichever transaction commits second cleans up the object the first one wrote, and the
   winner's object is the one the row points at. No lost object, no deleted-live-avatar. This is why
   `updateAvatar` is a modifier that returns a value.

3. **Order of operations: upload to S3 → update the row → delete the replaced object.** The analysis
   requires that a failed S3 upload must not update the database; putting the upload first satisfies that
   directly. The delete happens **last and non-fatally** — if the delete fails, the user still has a
   correct new avatar and the system has one orphaned object, which is a cleanup problem, not a user-facing
   failure. A failed delete is logged with the orphaned key and increments a metric so the leak is visible
   rather than silent. Deleting *before* the row update would have risked destroying a live avatar on a
   subsequent failure.

4. **Rejections are 422 with a machine-readable reason.** Both an oversized file and an unsupported format
   return `422` per the acceptance criteria, but with distinct `reason` codes (`too_large` /
   `unsupported_format`) and, for size, the actual and maximum byte counts. A single opaque 422 would meet
   the letter of the criteria and produce a useless error message.

5. **Content type is verified by magic bytes, not the client's declaration** — see the Interface Design
   note. This is a small addition beyond the literal analysis text, made because the literal reading leaves
   an SVG-upload path open.

6. **Timestamp comes from an injected `Clock`.** The key template embeds `<timestamp>`; using
   `Date.now()` directly would make key generation untestable and the concurrency behavior unreproducible.

## Deviations from Analysis
- **`avatar_key` column added, which the analysis did not list.** The analysis specifies only `avatarUrl`,
  but also requires deleting the previous S3 object. Deriving the old key by parsing it back out of a
  stored URL is fragile (it breaks the moment a CDN domain is put in front of the bucket). Storing the key
  alongside the URL is one nullable column and makes the delete path exact. Flagged for the architect and
  data-engineer to confirm.
- **`AvatarFile` and `Clock` were introduced as named types**, neither of which appears in the analysis's
  affected-files list. Both fall out of the complexity and testability rules rather than from new
  requirements.
- **Magic-byte content verification** goes slightly beyond the stated criteria (Key Decisions #5).
- **Tests were not written** — per this agent's rules, test authorship belongs to the QA engineer. Notes
  for QA below are correspondingly specific.
- **Nothing was actually executed**: no lint, no `tsc`, no test run (see Simple Design Verification #1).

## Notes for QA
- **The concurrency case is the one to hammer.** Fire two uploads for the same user at once and assert
  three things afterward: the `users` row points at exactly one key, that key's object exists in S3, and
  the *other* object has been deleted. A test that only asserts "the row was updated" will pass against the
  broken read-then-write implementation this was specifically written to avoid.
- **A failed S3 upload must leave the row untouched** — inject an adapter that rejects, then assert
  `avatar_url` is unchanged and the response is a 5xx, not a partial success.
- **A failed delete of the replaced object must NOT fail the request** — inject an adapter whose `remove`
  rejects and assert the user still gets a successful response with the new avatar, and that the orphan is
  logged.
- **422 cases**: a 2 MB + 1 byte file, a GIF, and an SVG. Also send an SVG with a `Content-Type:
  image/png` header — that one specifically exercises the magic-byte check and will pass trivially against
  a declaration-trusting implementation.
- **Exactly at the limit**: a file of exactly 2 MB must be *accepted* (the limit is "max 2 MB", so the
  boundary is inclusive). This is the off-by-one most likely to be wrong.
- **Key format**: assert the stored key matches `avatars/<user-id>/<timestamp>.<ext>` with the extension
  derived from the verified content type, not from the client's filename.
- **No AWS types leak**: an architecture test asserting nothing under `src/users/**` imports
  `@aws-sdk/client-s3` is worth adding as a fitness function.

## Notes for DevOps
- New env vars: `AWS_S3_BUCKET`, `AWS_REGION` (both named in the analysis) — needed in CI and production.
  Credentials come from the instance/task role or the secrets vault; no key material in source or in CI
  variables (`architecture-guardrails.md` #3).
- Migration `0031_add_avatar_url.sql` is **Expand phase**, additive, two nullable columns, no backfill and
  no lock of consequence — safe to run before the deploy.
- The bucket needs a **lifecycle policy** for orphaned objects. The delete path is best-effort by design
  (Key Decisions #3), so a small orphan rate is expected and must be swept, or storage grows without bound.
- Suggested alerting: a counter for failed avatar-object deletions. It is the signal that the orphan rate is
  climbing, and nothing user-facing will ever surface it.
