# Feature Analysis: Password Reset via Email

> **Spec Ingestion Security Check** (`shared/rules/memory-trust-boundary.md`): the spec was scanned for
> instruction-override patterns ("ignore", "override your instructions", "disregard previous", requests to
> skip an approval gate or grant tool permissions). **None found.** Every imperative in the spec is
> directed at the feature ("the reset link must be single-use"), not at the agent. Safe to proceed.

> **Context debt**: no `context-manifest.md` was produced for this feature (context-engineer was skipped),
> so scope below comes from reading the spec plus direct codebase exploration. `DOMAIN_DICTIONARY.md`
> exists but does not yet define **Reset Token** or **Notification Service** — see Tech Writer Tasks.

## Summary
Users who forget their password currently have no self-service path back into their account, and manual
resets consume 12% of inbound support volume. This feature adds a "Forgot password" flow: the user submits
an email address, the system issues a cryptographically random, single-use **Reset Token** that expires
after 30 minutes, and emails a link containing it through a **Notification Service** that does not exist in
this codebase yet. The business value is a direct reduction in support load; the domain value is that
Identity & Access gains its first outbound-communication capability, which every future transactional email
(verification, security alerts) will reuse. The hardest requirement is not the token — it is that the
response must be *indistinguishable* for registered and unregistered email addresses, which constrains
status codes, response bodies, and response timing simultaneously.

### Acceptance Criteria

- **AC1 — Reset request for a registered email**
  Given an email address that belongs to a registered account,
  When the user submits it to the reset-request endpoint,
  Then a reset email containing a single-use link is sent, and the response is `202 Accepted` with a
  generic body.

- **AC2 — Reset request for an unregistered email (no user enumeration)**
  Given an email address that belongs to no account,
  When the user submits it to the reset-request endpoint,
  Then no email is sent, and the response is byte-identical to AC1 (`202 Accepted`, same body, same
  headers) and within the same latency envelope.

- **AC3 — Token expiry**
  Given a reset token issued more than 30 minutes ago,
  When the user submits it with a new password,
  Then the request is rejected with a generic `400 Bad Request` and the password is unchanged.

- **AC4 — Single use**
  Given a reset token that has already been used successfully once,
  When the same token is submitted again,
  Then the second attempt is rejected and the password set by the first use remains in effect.

- **AC5 — Successful reset**
  Given a valid, unexpired, unused token and a new password meeting the *existing* complexity policy,
  When the user submits both,
  Then the account password is updated, the token is marked used, and all other outstanding reset tokens
  for that user are invalidated.

**Specification by Example** — token validation truth table (the ambiguity in "single-use and expires after
30 minutes" is exactly here, so it is tabulated rather than described):

| Token exists | Age at submit | `usedAt` | New password valid | Outcome | Response |
|---|---|---|---|---|---|
| yes | 5 min | null | yes | password updated, token marked used | `200 OK` |
| yes | 29 min 59 s | null | yes | password updated | `200 OK` |
| yes | 30 min 01 s | null | yes | rejected — expired | `400`, generic message |
| yes | 5 min | set | yes | rejected — already used | `400`, generic message |
| yes | 5 min | null | no (fails existing policy) | rejected — token NOT consumed | `422`, policy message |
| no (forged/garbage) | — | — | yes | rejected | `400`, generic message |

Note the fifth row: a policy failure must **not** burn the token, or a user who mistypes a weak password is
locked out of their own reset link. This is a real behavioral decision, not an implementation detail.

**Accessibility (a11y)** — the flow has UI (request form, confirm form), so:
- Both forms must be fully operable by keyboard alone, with a visible focus indicator on every control.
- The email and password fields must have programmatically associated `<label>` elements (not placeholder-only).
- Success and error messages must be announced to screen readers via an `aria-live="polite"` region — a
  purely visual color change is not sufficient.
- The new-password field must allow paste (password managers) and must not disable autocomplete
  (`autocomplete="new-password"`).

### Non-Functional Requirements
- **Performance**: the reset-request endpoint must enqueue the email and respond within **200 ms p95**;
  actual delivery is asynchronous. The outbound call to the email provider must carry an **explicit
  timeout (2 s connect / 5 s total)** — per `architecture-guardrails.md` #5, no network call may be
  unbounded, and no hand-rolled retry loop is permitted (use the framework's `ExponentialBackoffStrategy`
  behind a `CircuitBreaker`).
- **Security**: tokens are generated from a CSPRNG (≥ 256 bits of entropy), **stored hashed** (the raw
  token exists only in the emailed link — a database read must not yield usable tokens), single-use, and
  expire at 30 minutes. Reset-request and reset-confirm endpoints must both be rate limited. No email
  address, token, or password may appear in any log line or OTel span attribute.
- **Scaling**: low volume (est. < 1,000 requests/day). No sharding or partitioning concerns. The reset-token
  table will grow unboundedly without cleanup — a scheduled purge of expired/used rows is required, or the
  table becomes a slow leak.

## Proposed Fitness Functions
- **No user enumeration**: the reset-request response for a registered vs. unregistered email is identical
  in status code, body, and header set.
  - **Verification**: an automated acceptance test asserting byte-equality of both responses, plus a latency
    assertion that the two paths differ by less than the framework's timing tolerance. Runs in CI on every PR.
  - **Owner**: DevOps (wiring), QA (authorship)
- **Token TTL is enforced, not advisory**: no token older than `RESET_TOKEN_TTL_MINUTES` is ever accepted.
  - **Verification**: integration test with an injectable clock advancing past the boundary (29:59 accepted,
    30:01 rejected). Requires the clock to be behind an interface — see Developer Tasks.
  - **Owner**: Architect (clock interface), QA (test)
- **No secrets or PII in logs/spans**: no log line or span attribute contains an email address, raw token,
  or password.
  - **Verification**: CI check asserting span attributes for the reset flow match an allowlist, plus a grep
    fitness function failing the build on `logger.*` calls referencing `token`, `password`, or `email`.
  - **Owner**: DevOps
- **Email provider call is bounded**: every call into the notification adapter has an explicit timeout and
  is wrapped in a `CircuitBreaker`.
  - **Verification**: lint/architecture test asserting the adapter's outbound client is constructed with a
    timeout, and that no `for`/`while` + `sleep` retry loop exists in `src/notifications/`.
  - **Owner**: Architect
- **Reset request p95 < 200 ms**: measured at the endpoint, excluding actual email delivery.
  - **Verification**: k6 smoke run in CI against the staging deployment, threshold `p(95)<200`.
  - **Owner**: DevOps

## Out of Scope
- Changing the password complexity policy (explicit in the spec — the existing policy is reused as-is).
- Multi-factor authentication, including MFA re-verification during reset.
- Account recovery via any channel other than email (SMS, security questions, support-agent override).
- Session invalidation on password change — **flagged as an Open Question** below, because it is arguably
  a security requirement rather than a scope choice.
- A general-purpose notification/templating platform. This feature builds the *minimum* Notifications
  capability needed to send one transactional email; generalizing it now would be premature.

## Technical Breakdown

### Bounded Context
- **Owning Context**: Identity & Access — it owns the `User` aggregate, credentials, and now the
  `PasswordResetRequest` aggregate.
- **Context Crossings**: **Yes, and this is the architectural headline.** Identity & Access must trigger an
  outbound email, a capability that belongs to a **Notifications** context that does not exist yet. This is
  the first crossing of its kind in the codebase and the first external network dependency of its kind.
  Whether the crossing is a direct synchronous call to a Notifications adapter or an event
  (`PasswordResetRequested`) consumed asynchronously is **an architect decision, not an analyst one** — both
  satisfy the acceptance criteria, and the choice constrains every future transactional email. Escalated to
  the architect; the developer must not pick one by default.

### Domain Events (Event Storming Lite)
- **Commands**: `RequestPasswordReset(email)`, `ConfirmPasswordReset(rawToken, newPassword)`
- **Events Produced**: `PasswordResetRequested` (carries userId + tokenId, never the raw token or email),
  `PasswordResetCompleted`, `PasswordResetTokenExpired` (derived/observational — may be projected rather
  than emitted)
- **Owning Aggregates**: `User` (owns the credential), `PasswordResetRequest` (owns token lifecycle:
  issued → used | expired)
- **Read Models / Projections**: none user-facing. The UI never reads token state — it only submits and
  reads the generic outcome. An internal support/ops projection ("how many resets requested in the last
  24 h") is desirable for measuring the 12%-of-support-volume claim, but is not required for this feature.

### Affected Components
- `src/auth/` — new: reset-request and reset-confirm use cases, token generation and validation. This is
  where the existing credential logic lives, so the reset flow belongs beside it, not in a new top-level module.
- `src/auth/user.repository.ts` (or equivalent) — needs a `findByEmail` that returns the **same shape**
  (nullable) regardless of match, so callers cannot branch observably on existence.
- `src/notifications/` — **new module**. Contains the `NotificationService` port (defined in the use-case
  layer per `go/typescript` conventions and `CLAUDE.md`'s "interfaces in the consumer") and one adapter
  implementing it against the chosen email provider.
- HTTP routing layer — two new routes (see API Changes).
- Rate-limiting middleware — must be applied to both new routes; if no shared limiter exists, this is a new
  cross-cutting component and an architect concern.
- Clock abstraction — token expiry is time-dependent and must be testable; if the codebase has no `Clock`
  interface, one is needed (`CLAUDE.md`: every external dependency, including the clock, hides behind an
  interface).
- Frontend: forgot-password request form and reset-confirm form.

*Paths above are stated as modules rather than verified file paths because this analysis was produced
against a standalone spec fixture with no repository to explore. In a real run these MUST be verified with
Glob/Grep before the developer starts.*

### Data Model Changes
**Expand phase only** — entirely additive, safe to run before deploy:
- New table `password_reset_tokens`:
  - `id` (PK)
  - `user_id` (FK → users, indexed)
  - `token_hash` (unique, indexed) — SHA-256 of the raw token; the raw value is never stored
  - `expires_at` (timestamptz, NOT NULL, indexed for the purge job)
  - `used_at` (timestamptz, **nullable** — null means unused; this is meaningful absence, not a missing default)
  - `created_at` (timestamptz, NOT NULL, DEFAULT now())
- No changes to `users`. No column is dropped or renamed, so **no Contract phase is required in this
  release**. The only future Contract-phase work would be retiring the table if the feature is removed.
- Per `architecture-guardrails.md` #2: every NOT NULL column added here is on a *new* table, so the
  "NOT NULL without DEFAULT" hazard does not apply — but the migration must still be reviewed by the
  data-engineer before it runs.

### API Changes
Two new endpoints:
- `POST /auth/password-reset/request` — body `{ email: string }`. **Always** responds `202 Accepted` with
  `{ "message": "If that email is registered, a reset link has been sent." }`. Never `404`, never a
  different body — this response is a security control, not a UX nicety, and must be treated as such in
  review.
- `POST /auth/password-reset/confirm` — body `{ token: string, newPassword: string }`. Responds `200 OK` on
  success; `400` with a single generic message for invalid/expired/used/unknown token (the four cases must
  be indistinguishable); `422` with a specific message for a password failing the existing complexity policy
  (distinguishable because at that point the caller already proved token possession).
- Both bodies validated with a Zod schema at the boundary before any use
  (`architecture-guardrails.md` #4).

### New Dependencies
- **An outbound transactional email provider** (SES, SendGrid, Postmark, or equivalent) — the first external
  network dependency of its kind here. Provider selection, the resilience strategy around it, and whether it
  is reached synchronously or via a queue are **architect decisions**. Whatever is chosen must be hidden
  behind the `NotificationService` interface so the use-case layer never imports the provider SDK.
- A CSPRNG for token generation — use the platform's built-in (`crypto.randomBytes`), **not** a new
  package.
- Possibly a rate-limiter dependency if none exists in the codebase.

## Task List

### Developer Tasks
1. Define the `NotificationService` port in the use-case layer with a single method for sending a password
   reset email; no provider types may appear in its signature.
2. Define the `Clock` interface (or reuse an existing one) so token expiry is testable without sleeping.
3. Write the Expand migration creating `password_reset_tokens` per Data Model Changes above (additive only).
4. Implement `PasswordResetRequest` token issuance: CSPRNG raw token, store only its hash, set `expires_at`
   from `RESET_TOKEN_TTL_MINUTES` (default 30) read from configuration — no literal `30` in business logic.
5. Implement the reset-request use case with the enumeration-safe contract: look up the user, and whether or
   not one is found, return the identical `202` response. Ensure the not-found path does not short-circuit
   measurably faster than the found path.
6. Implement the reset-confirm use case: hash the submitted token, look it up, reject expired/used/unknown
   with one generic error; validate the new password against the *existing* policy; on success update the
   credential, set `used_at`, and invalidate the user's other outstanding tokens — all in one transaction.
7. Implement the email provider adapter behind `NotificationService`, with an explicit timeout and the
   framework's `CircuitBreaker`/`ExponentialBackoffStrategy`. No hand-rolled retry loop.
8. Wire Zod validation on both endpoints and rate limiting on both routes.
9. Add the scheduled purge of expired/used reset tokens.
10. Put the whole flow behind a feature flag (see below) so it can merge to trunk before the provider
    credentials exist in production.
11. Build the two frontend forms to the a11y requirements in the Acceptance Criteria.

**Feature Flag / Toggle strategy** (trunk-based development, mandatory): a single release toggle
`feature.password_reset_email` gates route registration for both endpoints and the "Forgot password?" link
in the UI. Default **off**. This lets migration, token logic, and the notification adapter merge to trunk
daily while the provider account and credentials are still being provisioned. The flag is a *release* toggle,
not an experiment toggle — it is removed in the release following full rollout, and that removal should be
tracked as a task at flag-creation time so it does not become permanent scaffolding.

### QA Tasks
1. Assert byte-identical responses (status, body, headers) for registered vs. unregistered email, plus
   comparable latency — this is the single most important test in the feature.
2. Token expiry boundary via an injected clock: 29:59 accepted, 30:01 rejected.
3. Single-use: second confirm with the same token fails, and the password from the first use still works.
4. Weak new password with a valid token: rejected with `422` **and the token is still usable afterward**
   (the truth-table row most likely to be implemented wrong).
5. Forged/garbage token returns the same generic `400` as an expired one.
6. Issuing a second reset invalidates the first outstanding token.
7. Email provider outage: the reset-request endpoint's behavior is defined and the circuit breaker opens
   rather than hanging; the user-facing response does not leak provider failure detail.
8. Log and span inspection: no email address, raw token, or password appears in either.
9. Rate limiting: repeated reset requests for the same email/IP are throttled.
10. a11y: keyboard-only completion of both forms, label association, and screen-reader announcement of the
    success/error message.

## Edge Cases and Risks
- **Timing side channel defeats the enumeration defense**: the "user not found" path skips hashing and
  email enqueueing and is therefore measurably faster. *Mitigation*: normalize the work done on both paths
  (or enqueue to the same async boundary before branching) and assert the timing in CI.
- **Password-policy failure burns the token**: a naive implementation marks `used_at` before validating the
  new password, locking out a user who typos. *Mitigation*: validate first, consume last, in one
  transaction — explicitly tested (QA task 4).
- **Raw tokens stored**: storing the token plaintext makes a database read equivalent to account takeover.
  *Mitigation*: store only the hash; the raw value exists solely in the emailed link. Enforce by schema
  review.
- **Email delivery failure is invisible**: if the provider silently drops the message, the user sees the
  same generic `202` and support load does not drop. *Mitigation*: emit a delivery-outcome metric and alert
  on delivery-failure rate — required for the feature to actually deliver its stated business value.
- **Reset link leaked via referrer or shared inbox**: a token in a URL can leak through referrer headers or
  a forwarded email. *Mitigation*: short TTL (already required), single use (already required), and no
  third-party scripts on the reset-confirm page.
- **Token table grows unboundedly**: low volume makes this slow, not dramatic — but it is still a leak.
  *Mitigation*: scheduled purge (DevOps task 5).
- **Risk — the Notifications context is under-designed under time pressure**: because this is the first
  transactional email, whatever shape ships here becomes the de facto standard for all future email.
  *Mitigation*: architect pass before implementation (already flagged); resist generalizing beyond one
  message type, but make the port's shape defensible.

## Open Questions
1. **Should a successful password reset invalidate existing sessions?** The spec is silent. Most reset
   flows exist *because* the account may be compromised, which argues for invalidating all sessions and
   refresh tokens. This is listed as Out of Scope above only because the spec did not ask for it — it needs
   an explicit product/security decision rather than an analyst's guess.
2. **Direct call or event for the Identity → Notifications crossing?** Deliberately left to the architect;
   flagged here so it is not silently defaulted by the developer.
3. **Is there an existing rate limiter?** If not, adding one is a cross-cutting architectural addition, not
   a task inside this feature, and should be sized separately.
4. **What is the exact generic message text?** It appears in the response body and the UI and is a security
   control; product and legal may have wording preferences.
