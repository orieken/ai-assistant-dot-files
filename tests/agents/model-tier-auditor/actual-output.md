# Model Tier Audit Findings

## Summary
- Total Agents Audited: **6**
- Schema Compliant: **3** (analyst, developer, agent-evaluator — see the enum caveat below)
- Warnings: **2**
- Violations: **2**

## Enum Discrepancy (must be resolved before any other finding can be acted on)

The audit rule and the corpus disagree about what the valid tier values *are*:

- `model-tier-auditor.md`'s own Rules section: `["light", "default", "heavy"]`
- The frontmatter samples under audit: `reasoning`, `standard`, `budget`
- `shared/contracts/agent-frontmatter-contract.md` and `shared/schemas/` are the authority and must be
  checked to settle it.

Under a literal reading of this agent's rule, **all six samples are violations**, including the three
reported as compliant — `reasoning`, `standard`, and `budget` are none of `light`/`default`/`heavy`. That
reading is almost certainly wrong: five of six agents use the reasoning/standard/budget vocabulary
consistently, and a live corpus in which every single agent violates the enum is much better explained by a
stale rule than by universal non-compliance.

So the findings below are graded against the **reasoning / standard / budget** vocabulary the corpus
actually uses, and this discrepancy is raised as finding zero. **A human must confirm which vocabulary is
canonical.** If `light`/`default`/`heavy` is correct, this is a corpus-wide migration and every finding
below is superseded by it. If reasoning/standard/budget is correct, `model-tier-auditor.md`'s own Rules
section is stale and needs updating — an auditor enforcing a vocabulary nothing uses will either produce
noise on every run or be quietly ignored, and both outcomes end with the check being disabled.

## Schema Violations

- `[context-engineer.md]`: **`model_tier` missing entirely.** The frontmatter carries `name` and
  `description` and nothing else. A missing tier is worse than a wrong one: a wrong value fails loudly at
  validation, while a missing one falls through to whatever the runtime default is, so the agent runs on an
  unstated tier that nobody chose and nobody reviews. It is also the specific failure that makes a
  portability claim false — the whole point of a declared tier is that another runtime can map it, and there
  is nothing here to map.

  Recommended value: **`reasoning`**. context-engineer's job is judgment about relevance — deciding which
  files matter, what to prune, which prior deliveries bear on this task. That is the same class of work as
  the analyst (also `reasoning`), and the cost of getting it wrong compounds: a bad manifest degrades every
  agent downstream of it.

- `[sre-engineer.md]`: **`model_tier: observability` is not a valid enum value** under either vocabulary.
  This is a category error rather than a typo — `observability` describes the agent's *subject matter*, not
  its computational tier. It reads as someone filling in a field by describing the agent instead of
  classifying its needs, which suggests the field's purpose is not obvious from its name alone.

  Recommended value: **`reasoning`**. sre-engineer reviews code for missing telemetry, judges log
  cardinality, and designs SLIs — analytical work over unfamiliar code, where the output is only as good as
  the judgment. `standard` would plausibly still produce a report; it would produce a shallower one, and
  nothing in the pipeline would notice.

## Heuristic & Alignment Warnings

- `[chaos-engineer.md]`: `model_tier: standard`, and the fixture's own annotation flags it —
  **write-heavy, autonomously executes bash.** This is the warning to take most seriously, and the reason is
  a blast-radius argument rather than an output-quality one.

  Its operational profile (`Read, Write, Edit, Bash, Glob, Grep` — fault injection designed and executed
  against a running system) is the highest-consequence profile in this sample by a wide margin. Every other
  agent here produces a document a human reads; this one takes actions against infrastructure. When a
  read-only auditor is under-tiered the result is a weaker report; when an agent that runs `bash` against
  live systems is under-tiered, the result is a badly-reasoned fault injection that has already executed.

  Recommended: **`reasoning`**, and — beyond this audit's remit but worth stating — an approval gate is the
  more important control here regardless of tier. Tier is not a safety mechanism.

- `[agent-evaluator.md]`: `model_tier: budget`, described as "Read-only; runs golden-file evaluations".

  **Half right, and the half that is wrong matters.** The pattern-matching half of a golden-file evaluation
  is mechanical — grep a file for regexes — and `budget` is correct for it. But this agent also grades
  output against a qualitative rubric, judging whether reasoning is *good*: correct severity, specific
  rather than generic fixes, no false positives. That is the hardest judgment task in the sample, and
  `budget` is a poor fit for it.

  There is a real tension here rather than a clear error, which is why it is a warning and not a violation:
  an evaluator that runs on every prompt edit is exactly where cost discipline belongs, and
  `cost-optimizer` exists to make that argument. But an under-tiered judge produces *confidently wrong
  grades*, and a wrong PASS is worse than no evaluation at all — it converts an absent check into a false
  assurance. Recommended: **`reasoning`** for the rubric pass specifically, or split the evaluation so the
  pattern half stays `budget` and only the judge half is promoted.

**Correctly tiered, for contrast** — an audit that lists only faults gives no signal about the baseline:
- `analyst.md` (`reasoning`): domain modeling, edge-case discovery, bounded-context judgment. Correct, and
  the errors it prevents are the most expensive in the pipeline because everything downstream inherits them.
- `developer.md` (`standard`): implementation against a completed analysis and architecture pass. The hard
  decisions were made upstream; this is skilled execution within a specified design. Correct.

      update whichever of the two is stale — this agent's Rules section, or the corpus. Every other finding
      here is downstream of that answer.
- [ ] **Add `model_tier: reasoning` to `context-engineer.md`.** A missing declaration is the one finding
      that silently does the wrong thing rather than failing.
- [ ] **Correct `sre-engineer.md` from `observability` to `reasoning`.**
- [ ] **Review `chaos-engineer.md`'s tier against its operational profile** — a `Bash`-executing,
      write-heavy agent at `standard` is the highest-consequence mismatch in this sample.
- [ ] **Decide `agent-evaluator`'s tier deliberately**, as a cost-versus-judgment trade-off rather than by
      default. Splitting the pattern pass from the rubric pass is the option that gets both.
- [ ] **For a human to consider**: two of six agents have an unusable `model_tier` (one missing, one
      invented). A JSON-schema check on agent frontmatter in CI would catch both at authoring time, which is
      cheaper than an audit finding them later. Proposed, not assumed — it is a real change with real cost.
