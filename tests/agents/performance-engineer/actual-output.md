# Performance & Reliability Report: Real-Time Notification Feed

**Headline before the sections**: the architecture as written does not survive its own stated scale
estimate. 10,000 concurrent long-polls against a connection pool of 10 is not a tuning problem to revisit
after launch — it is a design that cannot serve its second concurrent user cohort, and it will present as a
total outage of *every* database-backed endpoint in the service, not just the notification feed. That, plus
the missing index and the unbounded `SELECT *`, is the substance of this review.

## 1. Idempotency Guarantees
- **Status**: **N/A for the poll itself; Fail for the acknowledgment path that this design implies but
  does not specify.**
- **Notes**:
  - `GET /notifications/poll` is a read. It is naturally idempotent and needs no idempotency key.
  - However, the design's `read_at` column means notifications get **marked read** somewhere, and that
    write is not described anywhere in the architecture notes. If the poll itself sets `read_at` on
    delivery, then a client that crashes after the server writes `read_at` but before the payload is
    received **permanently loses those notifications**, with no way to recover them. That is a correctness
    failure caused by a performance-shaped design choice, which is why it belongs in this report.
  - **Mandate**: delivery and acknowledgment must be separate operations. The poll returns notifications
    and does not mutate `read_at`; a distinct `POST /notifications/read` carrying explicit notification ids
    performs the mark. That endpoint must be idempotent by construction — `UPDATE ... SET read_at = now()
    WHERE id = ANY($1) AND read_at IS NULL` is naturally so, since re-running it is a no-op. No
    `Idempotency-Key` header is needed given that shape; if the design instead marks by timestamp
    watermark, a key becomes necessary.

## 2. Timeout & Circuit Breaker Mandates
- **Status**: **Fail**
- **Mandates**:
  - **The 30-second poll must have a server-side timeout that is enforced independently of the client.**
    The design says a poll "waits up to 30 seconds" — that number must exist as an explicit, configured
    deadline on the server, not as an implicit consequence of a loop. A client that disconnects
    mid-poll must free the server resources immediately; otherwise abandoned polls accumulate faster than
    they expire.
  - **Every database query in this path MUST carry an explicit statement timeout** — 1000 ms is
    appropriate for the feed query. `architecture-guardrails.md` #5 makes this non-negotiable, and it
    matters more than usual here: a single slow query holding a connection from a pool of 10 stalls the
    entire service.
  - **The 30-second hold must not be implemented as a polling loop against the database.** If the handler
    wakes every 500 ms to re-run the feed query, 10,000 clients generate 20,000 queries per second at
    idle — the load is highest when nothing is happening. This is the most likely naive implementation and
    it must be excluded explicitly. Use `LISTEN`/`NOTIFY` (or an in-process event bus fed by the write
    path) so a waiting poll is woken by an event rather than by re-querying. **A hand-rolled
    retry/sleep loop is banned outright** by `architecture-guardrails.md` #5.
  - **Circuit breaker**: not applicable to the local database in the usual outbound-dependency sense — the
    correct behavior on database failure here is to fail fast with a 503 so clients back off, not to trip a
    breaker. What *is* required is a **bulkhead**: the notification feed must not be able to consume the
    connection pool that the rest of the application shares. Give the feed path its own bounded pool (or a
    semaphore capping concurrent feed queries) so its worst case is "the feed is degraded" rather than
    "the service is down".

## 3. N+1 Query Prevention
- **Status**: **Fail** — not from a classic N+1 loop, but from three related query defects that produce
  the same outcome (database work scaling with something it should not).

- **Findings**:
  1. **The index is missing, and the primary key does not help.** The query is
     `WHERE user_id = $1 AND read_at IS NULL ORDER BY created_at DESC`, and the notes state "No index
     defined yet beyond the primary key." The primary key is on `id`, which this query never touches. Every
     poll is therefore a **sequential scan of the entire `notifications` table**, and this table grows
     without bound. At 10,000 users polling every 30 seconds, that is roughly 333 full table scans per
     second. This alone is fatal.

     **Mandate** — a partial index matching the query exactly:
     ```sql
     CREATE INDEX CONCURRENTLY idx_notifications_unread_feed
       ON notifications (user_id, created_at DESC)
       WHERE read_at IS NULL;
     ```
     The `WHERE read_at IS NULL` clause makes this a partial index: it indexes only unread rows, which are
     a small and roughly constant fraction of the table, so the index stays small even as history grows.
     The `created_at DESC` ordering lets the sort be satisfied by the index rather than by a sort node.
     `CONCURRENTLY` is required so building it does not lock writes (`iac-conventions.md` and the
     Expand/Contract discipline both apply — this is a data-engineer hand-off).

  2. **`SELECT *` with no `LIMIT` is an unbounded result set** — a direct violation of
     `architecture-guardrails.md` #6. A user who ignores notifications for a month gets their entire
     backlog serialized into one response. The `payload JSONB` column makes this worse: each row is
     arbitrarily large, so the response size is unbounded in two dimensions at once.

     **Mandate**: `LIMIT 50` with **cursor-based pagination** on `(created_at, id)` — not `OFFSET`, which
     degrades linearly as the offset grows and is unstable when new rows arrive mid-pagination (exactly
     what a notification feed does). Replace `SELECT *` with the named columns the client actually needs.

  3. **Latent N+1 on the read model.** A notification feed almost always renders an actor ("Jane commented
     on…"). If `payload` holds a user id that the presentation layer resolves per notification, that is a
     textbook N+1 the moment the UI is built. **Mandate**: either denormalize the display fields into
     `payload` at write time (correct for a feed — notifications are immutable historical facts and should
     not re-resolve), or batch-load actors with a DataLoader. Decide now; discovering it after the UI
     exists means changing the write path.

## 4. Hot Path Caching
- **Analysis**: The structural problem is not query cost after the index lands — it is **connection
  holding**. The notes are explicit: "Each open poll holds a database connection for up to 30 seconds,"
  10,000 concurrent users, "Connection pool default: 10." That is a 1000:1 oversubscription. The 11th
  concurrent poll blocks, and because the pool is shared, so does every unrelated request in the
  application. Raising the pool to 10,000 is not the fix — Postgres will not sustain 10,000 backends, each
  costing several MB of server memory plus a process, and a connection pooler in transaction mode cannot
  help a connection held idle inside a transaction for 30 seconds.

  Long-polling itself is a defensible choice at this scale; **holding a database connection for the
  duration of the poll is not.** These are separable decisions, and conflating them is the root cause of
  everything in this section.

- **Strategy**:
  - **Release the connection immediately after the query.** A waiting poll must hold *no* database
    connection — it holds an in-memory waiter registered against the user id, and is woken by an event.
    Connections are then held for single-digit milliseconds per poll rather than 30 seconds, and a pool of
    20-50 comfortably serves 10,000 waiters. This is the single change that makes the design viable.
  - **Wake via `LISTEN`/`NOTIFY`** (one listener connection per process, not per user) or an in-process
    event bus fed by the notification write path. On wake, run the feed query once.
  - **Cache the unread *count* in Redis** with a 30-second TTL, keyed by user id, invalidated on write.
    Badge counts are read on every page load and change rarely; this removes the highest-frequency query
    from the database entirely. Cache the count, not the payloads — payload caching invites staleness for
    little gain.
  - **Cap waiters per process and shed load explicitly.** With a bounded waiter registry, exceeding it
    returns 503 with `Retry-After` rather than degrading everything silently. Explicit shedding beats
    implicit collapse.
  - **Archive or partition `notifications` by `created_at`.** The table only grows; the partial index keeps
    reads fast, but storage and vacuum cost will not stay flat. Not urgent, but decide the retention policy
    before launch rather than after the table is 500 GB.

## Notes for Developer

Concrete, in the order they should be done:

1. **Do not hold a database connection across the 30-second wait.** Query, release, then wait on an
   in-memory waiter woken by `LISTEN`/`NOTIFY` or an in-process event. If your handler holds a connection
   or an open transaction while waiting, the design is the broken one, not the tuning.
2. **Never implement the wait as a sleep-and-re-query loop.** Banned by
   `architecture-guardrails.md` #5, and it inverts the load profile so that idle is the most expensive
   state.
3. **Add the partial index before merging** (hand it to the data-engineer as a
   `CREATE INDEX CONCURRENTLY` migration). Verify with `EXPLAIN ANALYZE` that the feed query uses an
   index scan and has no sort node. Paste the plan into your implementation notes.
4. **`LIMIT 50` and cursor pagination on `(created_at, id)`.** Not `OFFSET`. Replace `SELECT *` with named
   columns.
5. **Explicit 1000 ms statement timeout** on the feed query, and an explicit server-side deadline on the
   poll that fires even if the client vanishes.
6. **Give the feed path its own bounded connection allocation** so it cannot starve the rest of the app.
7. **Separate delivery from acknowledgment.** The poll must not write `read_at`; add
   `POST /notifications/read` taking explicit ids.
8. **Decide the actor-resolution strategy now** — denormalize into `payload` at write time (recommended) or
   DataLoader-batch at read time. Do not resolve per notification.
9. **Load test before merge**, not after: k6 with 10,000 virtual users holding polls, asserting p95 poll
   response < 200 ms for the query portion, zero pool-exhaustion errors, and stable memory across a
   10-minute hold. The failure mode this design has is one that only appears under concurrency — a
   functional test suite will pass completely against the broken version.
