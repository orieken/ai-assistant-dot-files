# Code Review Report: Invoice.processAndPrint

## Overall Status
**CHANGES REQUESTED**

## Design Narrative
`Invoice` is a domain-named class that opens its own database connection, queries a row, walks the row's
line items in a hand-written index loop applying two hardcoded rate multipliers by string type code, writes
the result to stdout, and returns it. In plain English: it is a controller, a repository, a calculator, and
a printer wearing an entity's name.

That narrative took four clauses and an apology to write, which is the finding. Per this agent's own
process rule — if a coherent, succinct design narrative cannot be written, the implementation is too
complex and must be refactored before anything else is evaluated. Everything below is the specific version
of that one sentence.

## Design Score
- **Clarity** [2]: The class name says `Invoice`; the method name says `processAndPrint`. Neither tells the
  truth about what happens — `1.08` and `0.9` appear with no name attached, and `result.rows[0]` is
  untyped shapeless data flowing straight into business arithmetic. A reader cannot learn the tax rule from
  this code; they have to guess it.
- **Cohesion** [1]: Four responsibilities in nine lines of body — data access, iteration, pricing policy,
  and output. The method name's own `and` is the confession (`CLAUDE.md`: "if you need `and` in the name,
  split it").
- **Coupling** [1]: A domain-named class imports `pg` directly and constructs a module-level `Pool` at
  import time. This is the dependency-direction violation the framework treats as a hard constraint
  (`architecture-guardrails.md` #1), not a style preference. The coupling is also to a *singleton created as
  a side effect of importing the file*, so the class cannot be constructed in a test without a live
  Postgres.
- **Craft** [1]: This is a first draft. The Refactor step of Red-Green-Refactor was not taken — there is no
  Named Refactoring Log to check it against, because there is no `implementation-notes.md` at all.

**Three of four dimensions are below 3. CHANGES REQUESTED.**

## Security Surface
- `pool.query('SELECT * FROM invoices WHERE id = $1', [id])` is correctly **parameterized** — credit where
  due; this is the one thing the file gets right, and it should stay exactly as it is.
- `SELECT *` pulls every column of the invoices row into application memory, including any column added
  later (a customer tax identifier, a billing address). The subsequent `console.log` means whatever ends up
  in that row is one careless edit away from stdout. Select the columns you need.
- `console.log('Invoice ' + id + ' total: ' + total)` writes an invoice identifier and a monetary amount to
  unstructured stdout. This is not a credential leak, but it is business data in logs with no structure, no
  redaction boundary, and no correlation id.

## Performance Surface
- **Unbounded result set**: `invoice.items` is iterated with no bound. An invoice with 50,000 line items
  is loaded and summed in a single request with no pagination or streaming
  (`architecture-guardrails.md` #6).
- **No timeout**: `pool.query` is issued with no explicit statement or query timeout, so a slow query has
  no bounded failure mode (`architecture-guardrails.md` #5).
- **Latent N+1 risk**: `invoice.items` is read off `result.rows[0]` from a query that selects only from
  `invoices`. Either `items` is a JSON column (fine, but then the shape deserves a type), or this code is
  relying on an ORM that will lazy-load each item — which is an N+1 waiting to be discovered in production.
  This is unresolvable from the file alone and must be answered by the developer, not assumed.
- **Silent undefined**: if the id matches no row, `result.rows[0]` is `undefined` and
  `invoice.items.length` throws a `TypeError` rather than a domain error.

## Test Design Review
No tests accompany this file, and none could be written against it as structured — the module-level
`new Pool()` executes on import, so any unit test either connects to a real database or resorts to module
mocking gymnastics. That is the practical cost of the coupling finding, and it is the reason the fix below
is not cosmetic.

Once the calculation is extracted to a pure function over typed line items, the interesting tests become
trivial and behavior-focused: standard item taxed at the standard rate, discounted item taxed after
discount, unknown type passed through untaxed, empty item list totals zero, mixed basket. Those tests
verify *pricing policy*, which is the thing that will actually change — not `pool.query` call counts, which
is implementation detail.

## Feedback for the Developer

The parameterized query is right, and the branch structure of the pricing rules is readable. The problem is
not that this code is hard to follow — it is that it is four things at once, and one of those things
(database access) is on the wrong side of a boundary the framework treats as non-negotiable. Take these in
order; each one makes the next easier.

### 1. Move Method / Extract Class — get `pg` out of the domain
- **File**: `tests/agents/code-reviewer/input-smelly-code.ts` lines 1-3, 7
- **Smell**: A domain entity directly imports the `pg` `Pool` and constructs it at module scope.
  Inner layers importing outer layers is a hard architectural violation
  (`architecture-guardrails.md` #1), and the import-time `new Pool()` makes the class untestable without
  live infrastructure.
- **Instruction**: Define an `InvoiceRepository` interface in the use-case layer with
  `findById(id: string): Promise<Invoice | null>`, implement it in an adapter that owns the `pg` `Pool`,
  and inject it. `Invoice` must import nothing from `pg`. The `Pool` is constructed once in the composition
  root, not as a side effect of importing a domain file.

### 2. Extract Function — separate calculation from presentation
- **File**: `tests/agents/code-reviewer/input-smelly-code.ts` lines 6-19
- **Smell**: `processAndPrint` calculates a total **and** prints it. The `and` in the method name is the
  tell; this is the textbook Separate Query from Modifier violation.
- **Instruction**: Extract the summation into a pure `calculateTotal(items: LineItem[]): Money` with no
  I/O, and delete the `console.log` from this method entirely. Presentation belongs to the caller. If a
  log line is genuinely wanted, it belongs in the adapter/controller layer as a structured log with stable
  low-cardinality text, not string concatenation to stdout from a domain method.

### 3. Replace Magic Number with Symbolic Constant
- **File**: `tests/agents/code-reviewer/input-smelly-code.ts` lines 12, 14
- **Smell**: `1.08` and `0.9` are magic numbers embedded in business logic. `1.08` is a tax rate that will
  change by jurisdiction and by legislation; `0.9` is a discount policy. Both are business rules disguised
  as arithmetic, and today changing either means editing arithmetic in a domain method.
- **Instruction**: Introduce named values — `STANDARD_TAX_RATE` and `DISCOUNT_MULTIPLIER` at minimum, and
  preferably a `TaxRate` / `DiscountRate` value object sourced from configuration rather than a literal.
  Also note the duplicated `* 1.08` on both branches: extract the tax application so tax is applied once to
  a computed pre-tax amount, rather than repeated per branch (DRY, and it removes the risk of the two
  branches drifting apart when the rate changes).

### 4. Replace Conditional with Polymorphism (or a dispatch map)
- **File**: `tests/agents/code-reviewer/input-smelly-code.ts` lines 11-17
- **Smell**: An `if/else if/else` chain switching on the string type code `'standard'` / `'discounted'`.
  Adding a third item type means editing this method — Shotgun Surgery in waiting, and the string literals
  are magic strings on top of the magic numbers.
- **Instruction**: Replace the type-code chain with a dispatch map from item type to a pricing strategy
  (`Record<LineItemType, (item: LineItem) => Money>`), or with polymorphic `LineItem` subtypes each owning
  `priceWithTax()`. A dispatch map is the simpler of the two and is sufficient here — do not build a
  strategy class hierarchy for three cases. Make `LineItemType` a union type or enum so an unhandled type
  is a compile error rather than a silent fall-through to the untaxed `else`.

### 5. Replace Loop with Pipeline
- **File**: `tests/agents/code-reviewer/input-smelly-code.ts` lines 10-18
- **Smell**: A C-style indexed `for` loop with a mutable accumulator, repeatedly re-indexing
  `invoice.items[i]` (three times per iteration in two of the branches).
- **Instruction**: After operations 3 and 4, this collapses to
  `items.reduce((sum, item) => sum + priceOf(item), 0)` — or `items.map(priceOf).reduce(add, 0)`. Do this
  **last**; converting the loop before extracting the pricing rules just hides the magic numbers inside a
  lambda.

### 6. Introduce a typed shape for the query result
- **File**: `tests/agents/code-reviewer/input-smelly-code.ts` line 8
- **Smell**: `result.rows[0]` is implicitly `any` and flows straight into business arithmetic.
  `architecture-guardrails.md` #4 forbids raw `any`; and `undefined` on a missing id will throw a
  `TypeError` instead of a domain error.
- **Instruction**: Have the repository (operation 1) return a validated, typed `Invoice` — parse the row
  with Zod at the adapter boundary — and return `null` for a missing id so the caller handles absence
  explicitly. Replace `SELECT *` with the specific columns the domain needs.

**Please address 1 and 2 first** — they are the two that unblock testing. Once the repository interface
exists and the calculation is a pure function, operations 3-6 can be done with tests green under you, which
is the point. Re-request review when the Named Refactoring Log in `implementation-notes.md` lists what you
actually applied.
