# Add Dark Mode Toggle

## Summary
Users can switch the application to a dark color scheme from the settings page, and the app remembers
that choice on their next visit. This reduces eye strain in low-light conditions and matches an
expectation most users now bring from their operating system and other apps.

## Acceptance Criteria
- [ ] Given a user on the settings page, when they toggle dark mode on, then the interface switches to the
      dark color scheme immediately without a page reload.
- [ ] Given a user who has enabled dark mode, when they return to the app later in a new session, then the
      app is still in dark mode.
- [ ] Given a user who has enabled dark mode, when they toggle it off, then the interface returns to the
      light scheme and stays light on their next visit.
- [ ] Given a user who has never set a preference, when they open the app, then the app matches their
      operating system's light/dark setting. *(Assumed — see Open Questions Q1. If the intended default is
      "always light until chosen", this criterion is wrong and must be replaced, not adjusted.)*
- [ ] Given a user with dark mode enabled, when they view any page in the app, then all text meets a
      contrast ratio of at least 4.5:1 against its background.
- [ ] Given a keyboard-only user on the settings page, when they tab to the dark mode control, then it is
      focusable, operable with Space/Enter, and its on/off state is announced by a screen reader.

## Out of Scope
*Not stated by the requester.* Provisionally, and needing confirmation:
- Per-device (rather than per-account) preference
- A scheduled or automatic switch at sunset
- Themes beyond light and dark
- Dark-mode styling of transactional emails or PDF exports
- Restyling third-party embedded widgets

## Domain Language
- **Theme**: the named color scheme the interface renders in. Values: `light`, `dark`, `system`.
- **System preference**: the light/dark setting reported by the user's operating system or browser
  (`prefers-color-scheme`).
- **Theme preference**: the user's explicit stored choice, which may be `system` (defer to the OS).

*Requester introduced only "dark mode". The three terms above are proposed so the codebase does not end up
with `darkMode`, `theme`, `colorScheme`, and `nightMode` all meaning the same thing.*

## Non-Functional Requirements
- Theme switch is applied in under 100 ms with no full page reload.
- No flash of the wrong theme on initial page load — the stored preference must be applied before first
  paint.
- All text and interactive elements meet WCAG AA contrast (4.5:1 body, 3:1 large text) in **both** themes.
— *All three are proposed, not stated by the requester. Confirmation needed.*

## Trust Boundaries
- User-supplied theme preference is written to storage and read back on load. Low risk: the value must be
  validated against the allowed set on read rather than trusted, since a client-stored value can be
  tampered with — but it controls presentation only, and cannot reach any query or template unescaped.
- If the preference is stored server-side against the account (Open Questions Q2), it becomes an
  authenticated write to the user profile and inherits that endpoint's existing authorization.
— *No new authentication, no external calls, no sensitive data.*

## Test Approach
Saturday/Playwright — this is component and visual behavior rather than a business flow. Visual snapshot
baselines in both themes, plus an automated contrast check. A Cucumber scenario for the toggle-and-persist
journey would add little that the component tests do not already cover.

## Open Questions
- **Q1 — What is the default for a user who has never chosen?** Match the OS via `prefers-color-scheme`,
  or always start light? This is a product decision, not a technical one, and it changes an acceptance
  criterion. The draft assumes OS-matching because "remember their preference" implies a preference model
  that has an unset state.
- **Q2 — Is the preference per account or per device?** "Remember their preference" is ambiguous. Per
  account means a server-side profile field, a migration, and sync across devices. Per device means
  `localStorage` and no backend change. **This is the single biggest scope determinant in the feature** —
  it is the difference between a frontend-only change and one that touches the API and the database.
- **Q3 — Is there a designed dark palette?** If not, someone must produce one, and that is design work
  sitting on the critical path before any implementation starts. A palette invented by an engineer will
  fail the contrast criterion somewhere.
- **Q4 — Does the app render any user-generated or third-party content** (embedded charts, rich text with
  inline colors, iframes)? Those do not inherit a theme and are the most common source of unreadable
  patches in a dark-mode rollout.
- **Q5 — Is `system` an offered third option**, or only a binary toggle? The requester said "toggle",
  which implies binary, but that conflicts with Q1's OS-matching default.

## Infrastructure / Deploy Notes
Depends entirely on Q2. If per-device: none. If per-account: a new nullable `theme_preference` column on
the user profile (additive, Expand phase), a profile API change, and no environment variables either way.

## Spec Readiness Critique: Add Dark Mode Toggle

### Verdict
**NOT READY** — five open questions, two of which block downstream agents outright.

This is not a criticism of the request. "I want dark mode, toggled in settings, remembered" is a perfectly
good *ask*. It is simply not yet a spec: it does not say what "remembered" means, what happens before the
user chooses, or whether a dark palette exists. Those are the three cheapest things to answer now and the
three most expensive to discover during implementation.

### Agent Readiness

| Agent | Can it do its job? | Blocker |
|---|---|---|
| **Analyst** | ⚠️ Partially | Cannot determine the bounded context or whether a data model change exists until Q2 is answered. Per-device is presentation only; per-account touches the user profile aggregate. |
| **Architect** | ❌ No | Q2 decides whether there is a cross-layer change at all. There is nothing to make an architectural decision about until it is answered. |
| **Developer** | ❌ No | Q3 — without a defined palette there are no color values to implement. This is the blocker most likely to be discovered late, when it is a schedule problem rather than a question. |
| **QA** | ⚠️ Partially | Can test the toggle and persistence. Cannot test the default-state criterion while Q1 is open, and cannot verify contrast without Q3's palette. |
| **Security Reviewer** | ✅ Yes | Trust boundaries are narrow and named. Nothing here is security-sensitive beyond validating a stored value on read. |
| **DevOps** | ⚠️ Partially | Q2 again — either nothing to do, or a migration and a profile API change. |

### Required Changes
1. **Answer Q2 (per-account vs. per-device).** Everything else in the spec is downstream of this. It should
   take one sentence from a product owner and it unblocks three agents.
2. **Answer Q1 (default before any choice)** and reconcile it with Q5. "A toggle that defaults to the OS
   setting" is a three-state preference wearing a two-state control; that inconsistency will otherwise be
   resolved silently by whoever writes the code.
3. **Confirm whether a dark palette exists.** If not, add the design work to the plan explicitly rather
   than letting it be discovered by a developer picking hex values.
4. **Confirm the Out of Scope list.** Every item there is currently my assumption, not the requester's
   decision, and an unconfirmed out-of-scope list provides no protection against scope creep at all.
5. **Confirm the non-functional requirements**, particularly the no-flash-on-load requirement. It is the
   one that constrains implementation most (the theme must be applied before first paint, which usually
   means an inline script in the document head) and it is entirely my proposal.

### What's Strong
- The request is genuinely well-formed for its length: it names the user, the surface (settings page), and
  the persistence expectation. That is more than most one-line asks contain.
- The scope is naturally small and the trust boundaries are almost non-existent, so once the five questions
  are answered this will be a fast, low-risk delivery.
- Acceptance criteria came out cleanly falsifiable and free of implementation language — nothing in the
  request had to be pushed back on for describing mechanism instead of observable behavior.
