## Candidate Records (for surviving candidates only)

### Candidate: Use the raw `ws` package rather than Socket.IO for the notification feed
- **Source**: this session — a WebSocket notification feed was added directly to
  `src/notifications/ws-handler.ts` (240 lines, new file) with `ws` added to `package.json`.
- **Type**: ADR-worthy
- **Evidence**: "Used raw `ws` package instead of Socket.IO — *Socket.IO overhead not justified for this use
  case*"
- **Expiration condition**: this stops being the right call if the client side needs any of what Socket.IO
  provides and `ws` does not — automatic reconnection with backoff, transport fallback for restrictive
  networks, rooms/namespaces, or acknowledgement semantics. The moment any of those is hand-rolled on top of
  `ws`, the overhead argument has inverted and the decision should be revisited.
- **Existing overlap checked**: searched for "websocket", "socket.io", "ws", and "realtime" — **no
  matching KI or ADR found**. Caveat: this repository's KI corpus is about context and memory tooling, so
  the absence is weak evidence. The check must be repeated against the target project's corpus before this
  is filed.
- **Why ADR and not KI**: it is a decision with a rejected alternative and consequences that constrain
  future work, which is what an ADR records. A KI would be the reusable *pattern* that emerges from living
  with it — that comes later, if at all.

### Candidate: In-process EventEmitter fanout, deliberately deferring multi-instance support
- **Source**: this session — fanout for the notification feed was implemented with Node's `EventEmitter`
  rather than Redis pub/sub.
- **Type**: ADR-worthy
- **Evidence**: "Chose in-process event emitter (`EventEmitter`) over Redis pub/sub for fanout — *only one
  server instance in staging, will revisit for multi-instance*". And, from the session's own Notes: "The
  EventEmitter approach will silently break when a second server instance is added. This is a known future
  risk that was not documented."
- **Expiration condition**: **the moment a second server instance runs.** This is unusually crisp for an
  expiration condition, and it is why this candidate matters more than the other two.
- **Existing overlap checked**: searched "fanout", "pub/sub", "redis", "eventemitter", "horizontal scaling"
  — none found in this corpus (same caveat as above).
- **Why this is ADR-worthy and not a KI, correcting my first assessment**: a KI is reusable knowledge; this
  is a *time-limited local decision with a known expiry*. Filing it as a KI would propagate "use EventEmitter
  for fanout" as a pattern, which is the opposite of the intent — the decision is explicitly provisional.
  An ADR with status `Accepted (provisional)` records both the choice and its expiry condition.
- **Elevated priority, and this is the substance of the whole session**: the failure mode is *silent*. A
  second instance does not error, crash, or log — users connected to instance B simply never receive events
  produced on instance A. It will present as "notifications are flaky", will be blamed on the client, and
  will be extremely hard to diagnose without knowing this decision was made. The session notes state the
  risk was "not documented", which means the one artifact that would make the eventual incident a ten-minute
  fix does not exist. **This candidate should be filed even if every other one is rejected.**

### Candidate: OTel instrumentation deferred on the WebSocket handler, violating a hard constraint with no tracking
- **Source**: this session — no OpenTelemetry spans were added to `src/notifications/ws-handler.ts`.
- **Type**: Rule-change-worthy (enforcement gap, not a new rule)
- **Evidence**: "Did not add OpenTelemetry spans to the WebSocket handler — *will add later*", which the
  session itself annotates as violating `architecture-guardrails.md` §8.
- **Expiration condition**: closes when either the spans are added, or a CI fitness function exists that
  fails a build for an adapter-layer handler with no instrumentation.
- **Existing overlap checked**: `architecture-guardrails.md` §8 already states the rule — so the rule is not
  missing. Nothing needs to be added to `shared/rules/`.
- **What the candidate actually is**: guardrail §8 is stated as a hard constraint and was knowingly
  breached with a verbal "will add later" and no ticket. **A hard constraint that can be deferred by saying
  "later" is a guideline with a strong tone of voice.** The proposal for human review is therefore not new
  rule text but a decision about enforcement: either add a fitness function so §8 is mechanically
  enforceable (which `architecture-guardrails.md` §7 arguably already requires — "every structural decision
  must produce a fitness function"), or explicitly document that §8 is judgment-only, which §7 also permits
  provided the reason is recorded. Both are defensible; leaving it ambiguous is not, because the ambiguity
  is what allowed "will add later" to be a sufficient answer.
- **Not proposing the rule change myself**: this touches a hard constraint, and per
  `memory-trust-boundary.md` a conflict with a hard constraint is surfaced to a human, not resolved by an
  agent.
