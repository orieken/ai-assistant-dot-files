# QA Report: Password Reset via Email

Detail on the three behaviors the implementation notes specifically asked for:

**1. No user enumeration (AC2)** — five tests, because a single "same status code" assertion is exactly the
test that passes while the vulnerability remains:
- identical HTTP status for registered vs. unregistered email;
- byte-identical response body (deep equality on the parsed JSON, plus a raw-string comparison so a
  reordered key or a stray whitespace difference cannot slip through);
- identical response header sets, ignoring only `Date` and any request id;
- **latency parity** — 30 samples of each path, asserting the median difference stays within the
  framework's timing tolerance. This is the one that catches the real leak: the not-found path skips both
  hashing and enqueueing and is otherwise measurably faster;
- **no email is actually sent** for the unregistered address (the fake provider records zero sends), which
  is the flip side — the responses must match *and* the side effects must not.

**2. Token expiry (AC3)** — driven by the injected clock, at the boundary rather than in the middle:
- 29 min 59 s → accepted;
- 30 min 01 s → rejected;
- exactly 30 min 00 s → rejected (the boundary is exclusive; `expiresAt` is a deadline, not a grace
  period). This was ambiguous in the notes and is now pinned by a test — flagged for the tech writer;
- an expired token's rejection is **the same generic 400** as an unknown token's, so expiry is not itself
  an enumeration channel for "this token once existed";
- an expired token does not update the credential;
- `RESET_TOKEN_TTL_MINUTES` is honored — set to 5 in one test, and the boundary moves accordingly. Without
  this, a hardcoded `30` passes every other expiry test.

**3. Single use (AC4)** — reuse must fail, and the first use must survive:
- second confirm with the same token is rejected;
- after a successful reset, the password set by the *first* use still authenticates (a naive
  implementation can reject the second attempt while corrupting the credential);
- two concurrent confirms with the same token: exactly one succeeds, and the credential matches that
  winner — the `used_at` guard must be inside the transaction, not a read-then-write;
- issuing a second reset request invalidates the first outstanding token;
- **a new password that fails the complexity policy does NOT consume the token** — reject the password,
  leave the token usable. This is the highest-value test in the file and the one most likely to fail
  against a first implementation, because "mark used, then validate" reads perfectly naturally.

`[A11Y]` **carried forward as a gap, not a pass**: the password-reset flow has user-facing forms somewhere,

## Bugs Found
None confirmed — no suite was executed, so no bug can honestly be claimed as found or fixed. Two
implementation concerns surfaced while designing the tests and are raised rather than patched:

1. **`findByEmail` "returns `null` on no match, same shape either way"** covers the payload but says
   nothing about the *work* done on each path. Shape parity without timing parity leaves the enumeration
   channel open. The latency-parity test above is designed to fail if the not-found path short-circuits;
   if it does fail, the fix belongs to the developer, not to a loosened assertion.
2. **The expiry boundary at exactly 30:00 is unspecified** in the notes. The tests pin it as *expired*.
   If the implementation intends inclusive, that is a one-character difference and a test change — but it
   must be a decision, not an accident.

## Known Gaps
- **Coverage was not measured.** The 85% threshold is unverified. In a live run this alone blocks the
  handoff to tech-writer.
- **Real provider delivery is not tested.** The adapter is faked at the SDK boundary, so DKIM/SPF and
  actual inbox delivery are outside this suite. That belongs to a staging smoke test with a real sending
  domain — the feature can be fully green here and still deliver zero email in production, which is the
  single most important thing this report cannot tell you.
- **Rate limiting is not tested** because the implementation notes do not mention any. Both endpoints are
  unauthenticated and one of them sends email — untested rate limiting on this pair is a real gap, not an
  omission of convenience.
- **Session invalidation after reset is not tested** because it is not implemented. If the intent is that a
  reset kicks out existing sessions, there is no test asserting it and no code doing it.
- **Timing parity is inherently flaky in CI.** The 30-sample median approach reduces, but does not
  eliminate, noise on shared runners. If it proves unstable, the correct response is to make the two paths
  do genuinely equivalent work — not to raise the tolerance until the test stops complaining.

  behaves the way a real user's inbox will exercise it.
- Open the reset link twice in two browser tabs and submit both.
- Truncate, re-case, and URL-encode the token in the link — confirm all three produce the same generic
  rejection.
- Request a reset for an address that is registered but already locked or deleted.

### Shift-right (behind the feature flag)
With `feature.password_reset_email` enabled for a synthetic account only: a scheduled synthetic run that
requests a reset for a seeded mailbox, polls for delivery, follows the link, completes the reset, and
asserts end-to-end latency. This is what catches silent delivery failure, and it is safe in production
because it touches only the synthetic account.

## Notes for Tech Writer
- **The identical response for registered and unregistered emails is a deliberate security control**, not
  a missing 404. Document it as such, prominently — otherwise the next engineer "fixes" it, and every test
  above that guards it will look like an obstacle rather than a spec.
- **The 30-minute expiry boundary is exclusive**: a token at exactly 30:00 is rejected. Worth one sentence
  in the API docs, since "expires after 30 minutes" reads ambiguously.
- **A rejected new password does not consume the reset token** — the user can retry with the same link.
  This is user-visible behavior and belongs in the help article, because the opposite assumption ("my link
  is burned, request another") is what users will otherwise do.
- Document `RESET_TOKEN_TTL_MINUTES` (default 30) alongside the SES variables, including the operational
  consequence of lowering it.
- The rejection message is intentionally identical for expired, already-used, and unknown tokens. Do not
  document the three cases as distinguishable outcomes — they are not, on purpose.
