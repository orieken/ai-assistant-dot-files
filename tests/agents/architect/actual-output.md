# Architecture Notes: Password Reset via Email

## Structural Decisions

### 1. Identity & Access reaches Notifications through a port it owns, not a shared library

**Decision**: Define a `NotificationService` **port in the Identity & Access use-case layer** — the
consumer, per `CLAUDE.md` ("define interfaces in the consumer package, not the provider"). Its single
method takes a domain-shaped command (recipient user id + reset link), never a provider-shaped payload,
never an SDK type. The Notifications module supplies one adapter implementing that port. Identity & Access
does **not** import anything from `src/notifications/` except the port it defined itself; the wiring happens
in the composition root.

This is an **Anti-Corruption Layer** in the strict Evans sense: the email provider's vocabulary (templates,
message ids, delivery webhooks) stops at the adapter and never reaches the domain.

**Reversibility**: Cheap. The port is one interface with one method; swapping the adapter or moving to an
event-driven crossing (Decision 2) replaces the implementation without touching the use case.
**Fitness Function**: No file under `src/auth/` imports from `src/notifications/adapters/` or from any email
provider SDK package.
**Enforcement**: `dependency-cruiser` rule `no-auth-to-notification-adapters`, severity `error`, wired into
the existing `verify-dependencies` CI step.
**Responsibility**: devops-engineer wires it, architect defines it.

### 2. The crossing is a direct in-process call now, with the outbound send made asynchronous inside the adapter

**Decision**: Use a **direct synchronous call** from the reset-request use case to the `NotificationService`
port. Do **not** introduce a message broker, an outbox table, or a `PasswordResetRequested` domain event
consumed out-of-process for this feature. The 200 ms enqueue budget from the analysis is met by having the
adapter hand the send to an in-process background task and return immediately — the *use case* is
synchronous, the *delivery* is not.

The analysis correctly flagged direct-call vs. event-driven as an open architectural decision. Deciding it:
at < 1,000 requests/day with exactly one message type and no second consumer, an event bus is
**premature generalization** — it buys decoupling nothing currently needs, and costs a broker, a schema
registry, delivery-guarantee reasoning, and a second failure mode. Kent Beck's rule applies: fewest elements
that pass the tests. The port from Decision 1 is what makes this reversible — introducing an event later
means changing one adapter implementation, not the use case.

**Trade-off, stated explicitly**: an in-process background send means a process crash between "user gets
202" and "email leaves the building" loses that email silently. Accepted for this volume and this feature,
because the user-visible remedy (request another reset) is trivial and the link is short-lived anyway. This
is **not** acceptable for a future message type where loss is expensive (e.g. receipts) — at that point the
transactional-outbox pattern becomes required, and that is the trigger to revisit, not a vague "when we
scale".
**Reversibility**: Moderate. Reversing means adding an outbox + consumer behind the same port.
**Fitness Function**: The reset-request handler's p95 latency stays under 200 ms with the email provider
stubbed to a 3-second response — i.e. the request path genuinely does not block on delivery.
**Enforcement**: k6 threshold `p(95)<200` in the CI smoke job, run against a staging deploy with a slow
provider stub.
**Responsibility**: devops-engineer wires it, architect defines it.

### 3. The email provider is a new external dependency and is wrapped in the framework's stability primitives

**Decision**: The provider SDK is constructed **only** inside `src/notifications/adapters/`, with an explicit
timeout (2 s connect / 5 s total) and wrapped in the framework's `CircuitBreaker` +
`ExponentialBackoffStrategy`. No `for`/`while` + `sleep` retry loop is permitted anywhere in the path —
`architecture-guardrails.md` #5 is a hard constraint, not a preference. Credentials come from environment
variables backed by the secrets vault; no key literal may appear in source (`architecture-guardrails.md` #3).

This is the codebase's **first** external network dependency of this kind, so the shape chosen here becomes
the reference pattern for the next one. That is a reason for care, not a reason to build a general framework
now.

**Reversibility**: Cheap for the provider choice (it lives behind the port); Moderate for the resilience
shape, since later adapters will copy it.
**Fitness Function**: Every outbound HTTP client constructed in `src/notifications/` has an explicit timeout,
and no retry loop exists in that directory.
**Enforcement**: ESLint custom rule banning `setTimeout`/`sleep`-in-loop retry shapes under
`src/notifications/`, plus an architecture test asserting the adapter's client config carries a non-default
timeout. Fails the build.
**Responsibility**: devops-engineer wires it, architect defines it.

### 4. Reset tokens are stored hashed, and expiry is evaluated against an injected Clock

**Decision**: `password_reset_tokens.token_hash` stores a SHA-256 of a CSPRNG token; the raw token exists
only in the emailed link. Expiry is evaluated via a `Clock` interface defined in the use-case layer, not
`Date.now()` — otherwise the 29:59/30:01 boundary is untestable without sleeping, and an untestable
security control is an unenforced one.

**Reversibility**: Expensive for the hashing decision — reversing it means invalidating every outstanding
token and rewriting the schema, and the security posture would be strictly worse. Treat as settled.
**Fitness Function**: No column in `password_reset_tokens` ever holds a raw token value, and no call to a
wall-clock API appears in `src/auth/` outside the `Clock` adapter.
**Enforcement**: ESLint `no-restricted-syntax` banning `Date.now()` / `new Date()` under `src/auth/**`
(adapter directory exempted), plus schema review in the data-engineer's pass.
**Responsibility**: devops-engineer wires it, architect defines it.

### 5. The non-enumeration response is enforced at the handler boundary, not left to each code path

**Decision**: The reset-request handler builds its `202` response **before** branching on whether the user
exists — user lookup and email dispatch happen after the response shape is fixed. There is exactly one
`return` for this endpoint. This makes divergence a structural impossibility rather than a discipline
problem: there is no second response object for a reviewer to miss.

**Reversibility**: Cheap.
**Fitness Function**: Registered and unregistered email addresses produce byte-identical status, body, and
header set from the reset-request endpoint.
**Enforcement**: Acceptance test asserting response equality across both paths, run on every PR. This is the
fitness function the analysis called for; it is now assigned to CI rather than to reviewer vigilance.
**Responsibility**: devops-engineer wires it, architect defines it.

## Bounded Context
- **Context**: Identity & Access owns this feature, the `User` aggregate, and the new
  `PasswordResetRequest` aggregate.
- **Crossings**: One — Identity & Access → Notifications. It is the first crossing of its kind in the
  codebase.
- **Integration Pattern**: **Customer/Supplier via a consumer-defined port with an Anti-Corruption Layer.**
  Direct in-process call (Decision 2), not shared database (an anti-pattern here) and not an event bus (not
  yet justified). Notifications is a downstream *supplier* of a capability; Identity & Access defines the
  contract because it is the only consumer today.
- **Team Topology Fit**: **No `TEAM_TOPOLOGY.md` exists in this fixture run**, so team ownership and the
  declared Interaction Mode for this crossing could not be checked — reported rather than guessed. In a live
  run, `team-topology-check` must be invoked here: if Notifications is destined to be a Platform-team
  service consumed X-as-a-Service, a direct in-process call from Identity & Access is a Distributed Monolith
  smell at the team level even though it is structurally clean at the code level.

## Stability Design
| Dependency | Timeout | Circuit Breaker | Bulkhead | Fail Fast | Idempotency |
|---|---|---|---|---|---|
| Email provider (SES/SendGrid) | 2 s connect / 5 s total | Yes — framework `CircuitBreaker`; open circuit degrades to "queued, not sent" and increments a failure metric, never surfaces to the user | Background send pool capped (e.g. 16 in flight) so a provider stall cannot exhaust request threads | No — send failure must not fail the user's request; the `202` is already committed | Idempotency key = reset token id, so a retried send cannot produce two distinct valid links |
| Database (token read/write) | Inherited pool timeout, explicit statement timeout on the confirm transaction | No — a broker-less local dependency; failing fast is correct | Uses the existing shared pool | Yes — a DB failure on confirm must return an error, not a partial reset | Confirm is idempotent by construction: `used_at` set inside the same transaction as the credential update |

**Failure modes explicitly designed for**: provider outage (circuit opens, metric + alert, users see the
same generic 202), provider slow (timeout + bulkhead prevent request-thread exhaustion), duplicate confirm
(single transaction with `used_at` guard makes the second attempt a no-op rejection, not a double write).

## Observability Design
- **Spans**: `auth.password_reset.request`, `auth.password_reset.confirm`,
  `notifications.email.send`. Attributes: `user_id` (only where already resolved), `token_id`,
  `outcome` (`issued` | `sent` | `expired` | `used` | `invalid`), `provider`. **Explicitly excluded**:
  email address, raw token, password, provider API key. Per `architecture-guardrails.md` #8, spans are
  emitted from the controller/adapter layer only — never from the `PasswordResetRequest` entity or the use
  case.
- **Metrics** (low cardinality — no email, no user id as a label):
  `password_reset_requests_total{outcome}`, `password_reset_confirms_total{outcome}`,
  `email_send_failures_total{provider}`, `email_circuit_state{provider}`,
  `password_reset_request_duration_seconds` (histogram).
- **Logs**: structured, stable low-cardinality message strings — `"password reset requested"`,
  `"password reset confirmed"`, `"password reset rejected"` with `token_id` and `outcome` as fields. The
  rejection log must **not** distinguish expired / used / unknown in a way that a log-reading integration
  could re-expose; keep the discriminator in a field, not the message.
- **Alerts**: (a) `email_send_failures_total` rate > 5% over 15 min — the feature can appear healthy while
  delivering nothing, which is its most dangerous silent failure; (b) circuit breaker open for > 5 min;
  (c) confirm-success rate falling below its historical band, which is the signal that links are expiring
  before users click them.

## Layer Boundary Checks
- [x] No domain logic in adapter layer — the adapter translates and sends; expiry and single-use invariants
      live on the `PasswordResetRequest` aggregate.
- [x] No framework imports in use case layer — the use cases see `NotificationService`, `Clock`, and
      `ResetTokenRepository` ports only; no provider SDK, no HTTP types.
- [x] New components follow dependency direction (inward only) — `src/notifications/adapters` depends on the
      port defined in `src/auth`; nothing in `src/auth` depends on `src/notifications`.
- [x] No direct HTTP calls outside adapter implementations — the provider SDK is constructed only in
      `EmailNotificationAdapter`.

## Anti-Pattern Check
- [x] **Distributed Monolith** — checked. Avoided by *not* splitting Notifications into a separate
      synchronously-coupled service; it is a module behind a port. Flagged for re-check once a second
      consumer exists.
- [x] **Anemic Domain Model** — checked, and this is the live risk. `PasswordResetRequest` must own
      `isExpired(clock)` and `markUsed(clock)`; if those land in a `PasswordResetService` while the entity
      is a bag of fields, the model is anemic. Called out in Developer Handoff Notes.
- [x] **God Object** — checked. Deliberately two use cases (request, confirm) rather than one
      `PasswordResetService` doing both; they have different reasons to change.
- [x] **Shotgun Surgery** — checked. Changing the TTL touches configuration only, not multiple classes,
      because the literal `30` appears nowhere in business logic.
- [x] **Leaky Abstraction** — checked. `NotificationService` takes a domain command, not a provider template
      id; a caller does not need to know which provider is behind it.
- [x] **Premature Generalization** — checked, and actively resisted: no event bus (Decision 2), no generic
      templating engine, no multi-channel `NotificationService` with SMS/push methods that nothing calls.
      One method, one message type.
- [x] **Team Topology Fit** — checked to the extent possible; **no `TEAM_TOPOLOGY.md` row exists**, so this
      is reported as unverifiable rather than passed.

## Fitness Functions
These properties must remain true as the codebase evolves. Add these to CI if not already enforced:

- **auth-does-not-import-notification-adapters**: no import from `src/auth/**` into
  `src/notifications/adapters/**` or any email provider SDK — `dependency-cruiser` rule, severity error.
- **no-unbounded-network-calls**: every client constructed under `src/notifications/**` has an explicit
  timeout, and no `sleep`-in-loop retry exists there — ESLint custom rule + architecture test.
- **no-wall-clock-in-auth**: no `Date.now()` / `new Date()` under `src/auth/**` outside the clock adapter —
  ESLint `no-restricted-syntax`.
- **enumeration-parity**: reset-request responses for registered vs. unregistered emails are byte-identical
  in status, body, and headers — acceptance test on every PR.
- **request-path-does-not-block-on-delivery**: reset-request p95 < 200 ms with the provider stubbed at 3 s —
  k6 threshold in the CI smoke job.
- **no-secrets-in-spans**: span attributes for the reset flow match an allowlist that excludes email, token,
  and password — automated span-attribute check.

## Refactoring Opportunities
- `user.repository`: `findByEmail` must return the same nullable shape on both paths. If the existing
  repository throws a `NotFoundError` for missing users (a common shape), that exception is itself an
  enumeration channel once it reaches a handler → apply **Replace Exception with Test** so the reset path
  branches on a value, not a throw.
- Configuration access: if TTLs and provider settings are currently read ad hoc from `process.env` at call
  sites, apply **Introduce Parameter Object** to gather reset-flow settings into one typed config object —
  otherwise `RESET_TOKEN_TTL_MINUTES` becomes the next magic value scattered across files.
- No other adjacent smells identified; this feature is largely greenfield, so most of the Boy Scout surface
  is in the two touch points above.

## Developer Handoff Notes
- **Put the invariants on the aggregate.** `PasswordResetRequest.isExpired(clock)` and `.markUsed(clock)`
  belong on the entity. If you find yourself writing `if (token.expiresAt < now)` inside a use case, that is
  the anemic-model smell this document flagged — move it.
- **Build the `202` response object before you look the user up.** Decision 5 is structural on purpose: one
  return statement means the two paths cannot drift.
- **Do not consume the token before validating the new password.** The analysis's truth table has this row
  for a reason; the transaction order is validate → update credential → set `used_at`, all in one
  transaction.
- **Import the port from `src/auth`, not from `src/notifications`.** The adapter implements a contract it
  does not own. If your import direction is the other way, the dependency-cruiser rule will fail the build —
  which is the intended feedback, not an obstacle to route around.
- **The provider SDK appears in exactly one file.** If it appears in two, the ACL has already leaked.
- **`30` is configuration, not a literal.** Read `RESET_TOKEN_TTL_MINUTES`, default 30, at the config
  boundary.
- **No hand-rolled retries.** Use the framework `CircuitBreaker` and `ExponentialBackoffStrategy`. This is a
  hard guardrail, not a style preference.

## Open Architectural Questions
- **Does a completed reset invalidate existing sessions?** The analysis listed this as out of scope because
  the spec was silent, but it is a security posture decision with structural consequences: it requires
  Identity & Access to reach a session store, which is a second crossing this document has not designed.
  **Needs a human answer before the developer starts** — retrofitting it later is materially more expensive
  than including it now.
- **Which provider?** SES vs. SendGrid vs. Postmark does not change any decision above (that is the point of
  the port), but it does have DNS/lead-time consequences for DevOps and should be chosen this week.
- **Is there an existing rate limiter?** Both endpoints require one. If none exists, adding it is a new
  cross-cutting component and needs its own architectural pass — it is not a task inside this feature.
