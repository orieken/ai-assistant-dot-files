# Context Audit: rate-limit-feature

## Summary
- Context Manifest Present: **Yes**
- Total Pinned Files: **7** (4 source, 2 ADRs, 1 KI)
- Unused Pinned Files: **2** (1 never opened, 1 unrelated)
- Broken References: **1**

Four findings, of which one is Critical. The manifest is broadly sound — the three source files that matter
are correctly identified and ADR-007 is exactly the right decision record for this task — but roughly 30% of
the pinned context earned no keep, and the budget figure is off by 64%.

## Findings

### Broken References (Critical)
- [`ki-jwt-validation.md`]: Referenced under KI Links but **does not exist** under `shared/knowledge/` or
  `.claude/knowledge/`. The manifest itself records the absence, which means it was noticed and pinned
  anyway rather than removed.

  This is the Critical finding for a reason that is easy to miss: a broken KI link does not merely waste
  context, it produces a *false negative on institutional memory*. An agent reading this manifest concludes
  that JWT validation knowledge has been consulted. It has not — there is nothing to consult. The downstream
  agent then proceeds believing a check happened, which is worse than knowing it did not.

  The likely cause is worth naming: the name is plausible and adjacent to the correctly-pinned
  `auth.middleware.ts` ("JWT validation; rate-limit hooks go here"), so this reads as a KI that was assumed
  to exist because it *should* exist rather than because it was verified. If JWT validation patterns are
  genuinely worth capturing, the correct outcome is a `create-ki` task, not a dangling link.

### Unused Pinned Context (Pruning Candidates)
- [`src/models/user.model.ts`]: Pinned and, per the manifest's own annotation, **never opened** during
  implementation. Speculative pinning — plausibly reasoned ("rate limiting is per-user, so surely the user
  model is relevant") but wrong: per-user rate limiting needs a user *identifier* off the request, which
  arrives from the auth middleware, not the user aggregate. This is the single most instructive finding in
  the audit, because the reasoning that produced it will recur.

- [`docs/adrs/ADR-003-enterprise-memory-sync.md`]: **Unrelated to rate limiting.** Enterprise memory sync
  and API rate limiting share no subject matter. The manifest annotates it as an apparent copy-paste error,
  and the shape supports that — ADR-003 sits adjacent to the correctly-pinned ADR-007 in the same directory,
  which is exactly how a wrong ADR gets pinned alongside the right one.

  Worth separating from the previous finding: the user model was a *reasoning* error (a defensible guess
  that turned out wrong), while this is a *mechanical* error (the wrong file was copied in). They need
  different remedies — the first needs better pruning discipline, the second needs a verification step.

**Correctly pinned, for contrast** — an audit that only lists faults gives no signal about what good looks
like:
- `src/middleware/auth.middleware.ts` — the insertion point; correct and load-bearing.
- `src/cache/redis-client.ts` — the sliding-window counter's storage; the pin without which the task cannot
  be designed.
- `src/routes/api.router.ts` — needed to identify affected routes.
- `docs/adrs/ADR-007-rate-limiting-strategy.md` — the directly relevant decision record.
- `shared/knowledge/ki-redis-patterns.md` — exists and is on-topic.
- `deliver-feature/rate-limit-v1/implementation-notes.md` — a prior delivery in the same bounded context,
  correctly surfaced. This is the pin most often missed entirely, and its presence is a genuine strength.

### Budget Accuracy
- Budget status: **Warning** — a **budget discrepancy of 7,200 tokens**: the manifest claims 18,400 tokens
  against an actual pinned-file total of 11,200, overstating usage by 64%.

  The direction matters and cuts both ways. Overstating is less dangerous than understating — nothing
  overflowed — but it is not harmless: a manifest that claims 18,400 against a tier budget may trigger
  unnecessary cuts, and more importantly, **an inaccurate budget figure cannot be trusted in either
  direction**. The next manifest that understates by 64% will look exactly as credible as this one.

  There is also a consistency question this audit cannot resolve from the manifest alone: 11,200 is the sum
  of the *seven* pinned files including the two unused ones and the broken link (which contributes zero
  tokens, since the file does not exist). If the 18,400 figure was computed before the broken link was
  discovered, part of the gap may be a phantom file counted at an assumed size. **Verifying that would
  require reading the manifest's calculation, which is not shown** — flagged as a hypothesis, not a
  conclusion.

  After pruning the two unused pins, the effective figure drops further. The manifest should be recomputed
  rather than adjusted.

## Recommendations
- [ ] **Resolve `ki-jwt-validation.md` before the next pipeline run** — either correct the link if the KI
      exists under another name, or remove it and raise a `create-ki` task if the knowledge is worth having.
      Leaving a dangling KI link is the one finding here that actively misleads a downstream agent.
- [ ] **Remove `src/models/user.model.ts` and `ADR-003` from the manifest.** Not pruned by this agent —
      context-auditor reports, it does not edit.
- [ ] **Recompute the token budget after pruning** rather than editing the claimed number. A corrected
      figure derived from the same faulty calculation is not an improvement.
- [ ] **For context-engineer, the generalizable lesson**: both unused pins share a signature — pinned by
      *topical adjacency* rather than by an identified need. The user model is adjacent to "per-user";
      ADR-003 is adjacent to ADR-007 in the directory listing. A useful discipline for the next manifest is
      to state, per pin, the specific question that file answers. "Rate limiting is per-user" is a topic;
      "where does the authenticated user id come from" is a question — and its answer is the auth
      middleware, not the user model.
- [ ] **For a human**: consider whether the budget calculation should be mechanical rather than
      hand-estimated. A 64% error on a figure that exists precisely to be trusted suggests estimation, and
      summing file sizes is a scriptable operation.
