# Observability & SRE Report: Payment Webhook Handler

## 1. Service Level Indicators (SLIs)
*These metrics define the health of the newly added feature.*

This endpoint has an unusual property that shapes every SLI below: **the caller is Stripe, not a user, and
Stripe retries on 5xx.** That means a 500 is not simply "an error" — it is a request for redelivery. An SLI
built on HTTP status alone will therefore look healthy in the exact scenario that matters most (events
accepted with a 200 but never applied to an order).

- **Availability SLI**: `POST /webhooks/stripe` returns a non-5xx response for > 99.9% of requests over a
  rolling 28-day window. Signature-verification rejections (4xx) count as *successes* for availability —
  they are the endpoint working correctly — but are tracked separately as a security signal.
- **Latency SLI**: p95 end-to-end handler latency < 500 ms, p99 < 2 s. Stripe expects a timely response
  and treats a slow handler as a failure; the budget must sit well inside Stripe's own timeout.
- **Correctness SLI (the one that actually matters, and is currently unmeasurable)**: > 99.99% of
  `payment_intent.succeeded` events received result in the corresponding order reaching `paid` state within
  60 seconds. This cannot be computed from anything the current code emits — see Missing Telemetry. Without
  it, the two worst failure modes of this handler are invisible: an event silently dropped because its type
  was unrecognized, and an event acknowledged with a 200 while the order was never updated.
- **Freshness SLI**: p99 lag between the Stripe event's `created` timestamp and local processing < 120 s.
  This is what catches a backed-up retry queue, which the availability SLI will not.

Error budget: 0.1% of 28 days ≈ 40 minutes of full unavailability. Since Stripe retries with backoff for up
to ~3 days, a short outage is recoverable — which is an argument for spending the budget on *correctness*
alerting rather than on availability paging.

## 2. OpenTelemetry & Tracing
- **Analysis**: **Fail**
- **Spans Added**: **None.** No OpenTelemetry instrumentation exists anywhere in the three files described.
  There is no root span for the webhook request, no child span around `constructEvent()`, no span around
  the `stripe` client call, and no span around `markAsPaid`. The implementation notes do not mention
  tracing at all — this is not a partial instrumentation, it is a complete blind spot.

- **Missing Telemetry** (each of these is a real blind spot, not a completeness checkbox):
  - **`payments.webhook.receive`** — root span on the handler. Attributes: `stripe.event.type`,
    `stripe.event.id`, `webhook.outcome` (`applied` | `ignored_unhandled_type` | `signature_rejected` |
    `failed`), `http.status_code`. The `webhook.outcome` attribute is the single highest-value addition
    here, because it is what distinguishes "200, work done" from "200, event silently dropped" — and the
    notes confirm the code deliberately conflates those two by returning 200 for unrecognized types.
  - **`payments.webhook.verify_signature`** — child span around `stripe.webhooks.constructEvent()`. Records
    verification outcome and failure reason class (`bad_signature` | `stale_timestamp` | `malformed`).
    Without it, a rotated-but-not-updated `STRIPE_WEBHOOK_SECRET` presents as a wall of 4xx with no
    attributable cause.
  - **`stripe.api.request`** — child span in `stripe-client.ts` for any outbound call, with
    `peer.service = stripe`, the operation name, and duration. **Trace context does not propagate to
    Stripe** (it is a third party), so this span is where the outbound boundary becomes visible at all.
  - **`orders.mark_as_paid`** — child span in `order-service.ts` with `order.id` and the DB statement
    duration. When `markAsPaid` throws and the endpoint 500s, this is the only place the *reason* will be
    recoverable.
  - **Retry correlation**: Stripe redelivers the same `event.id`. Set `stripe.event.id` as a span attribute
    on every retry so all attempts for one event are queryable as a set. Without it, the fifth retry of one
    broken event is indistinguishable from five distinct failures — an important difference when judging
    blast radius during an incident.
  - **Span placement rule** (`architecture-guardrails.md` #8): all of the above are emitted from the
    handler and adapter layers. `order-service.markAsPaid` sits close to the domain — its span belongs at
    the repository/adapter boundary it calls, not inside domain logic.

## 3. Log Quality & Cardinality
- **Status**: **Fail** (not "Fixed" — the files do not exist in this repository, so no `Edit` was possible;
  the exact required changes are specified below and remain unapplied)
- **Findings**:
  - **The silent drop is the headline.** "Unrecognized event types are silently dropped (200 response to
    avoid Stripe retries)" — returning 200 is the right call (Stripe should not retry something we will
    never handle), but *silently* is not. Dropping an event with no record means an unhandled event type
    that later becomes business-critical produces zero evidence it was ever received. Required: a
    structured `info` log with a stable message string, e.g.
    `logger.info({ event_type, event_id, outcome: 'ignored_unhandled_type' }, 'stripe webhook ignored')`,
    plus the counter in Notes for DevOps below.
  - **Stable strings, variable fields.** Any log added here must use a fixed message string with
    variables as structured fields — never `` `Processing event ${event.id}` ``. Interpolated ids in the
    message string make every line unique, which defeats log aggregation and grouping and is exactly the
    cardinality failure `go-conventions.md` warns about.
  - **`markAsPaid` failure is under-logged.** The notes say a throw becomes a 500 and Stripe retries. There
    is no evidence of an error log carrying `order_id`, `event_id`, and the error class before the 500 is
    returned. As written, an operator's only signal is a bare 500 with nothing to correlate.
  - **Cardinality budget on fields**: `event_type` is bounded (a few dozen Stripe types) and is safe as a
    *metric label*. `event_id` and `order_id` are unbounded and must appear as **log/span fields only,
    never as metric labels** — putting `order_id` on a Prometheus counter would create one time series per
    order.
  - **No log level discipline is described.** Recommended: `info` for applied/ignored outcomes, `warn` for
    signature rejection (it is expected under key rotation, but a spike is an attack signal), `error` for
    an exception path that returns 500.

## 4. PII Data Hygiene
- **Status**: **Violation detected — mandated fix specified below, NOT applied (files absent from this
  repository)**

This is a deviation from this agent's standing rule that PII violations are fixed directly with `Edit`
rather than left as recommendations, and it is called out here rather than glossed: the fix could not be
applied because `src/payments/webhook-handler.ts` does not exist in this repo. It must be applied before
this feature ships.

- **The violation**: Stripe event payloads routinely contain cardholder name, billing address, email,
  the card's last four digits, and payment-method metadata. The handler receives the full event object,
  and the notes describe no redaction, no field allowlist, and no restriction on what is logged or
  attached to spans. Any future "log the event for debugging" line — the single most likely next edit to
  this file — dumps cardholder PII into log storage. Under PCI-DSS scope this is a reportable problem, not
  a hygiene nit.
- **Required fix** (exact): never log or span-attach the event object or `event.data`. Extract only
  `event.id`, `event.type`, and the internal `order_id` at the top of the handler and pass *those* forward;
  the raw event must not escape the function. Add a span-attribute allowlist for
  `payments.*` spans containing exactly `stripe.event.id`, `stripe.event.type`, `order.id`,
  `webhook.outcome`, `http.status_code` — anything else is dropped by the processor.
- **Second violation — secret in error paths**: `STRIPE_WEBHOOK_SECRET` is read in this path. Verification
  libraries have been known to include configuration in thrown error messages; if that error is logged
  verbatim, the signing secret lands in logs. Required: catch verification errors and log only a
  classified reason string, never the raw error object.
- **Clean**: no PII is written to the database by this change — `markAsPaid(orderId)` takes an id only.
  The exposure is entirely on the telemetry side.

## Notes for DevOps Engineer

**Metrics to create** (all low-cardinality; `order_id` and `event_id` are deliberately absent from every
label set):
- `stripe_webhook_events_total{event_type, outcome}` — counter. `outcome` ∈ {`applied`,
  `ignored_unhandled_type`, `signature_rejected`, `failed`}. This one counter makes the silent-drop
  behavior visible and is the prerequisite for the correctness SLI.
- `stripe_webhook_duration_seconds{event_type}` — histogram, for the latency SLI.
- `stripe_webhook_signature_failures_total` — counter, split from the general failure counter because its
  causes (rotated secret, attack) are entirely different.
- `orders_mark_as_paid_failures_total{error_class}` — counter. `error_class` is a small enumerated set,
  not the exception message.
- `stripe_webhook_event_lag_seconds` — histogram of (now − `event.created`), for the freshness SLI.

**Alerts to wire up**:
1. **`ignored_unhandled_type` rate > 0 sustained for 15 minutes** — page nobody, but ticket it. A new
   Stripe event type arriving in volume means the integration is silently out of date. This is the alert
   the current implementation makes impossible.
2. **`orders_mark_as_paid_failures_total` rate > 1% over 10 minutes** — page. Payments are being received
   and not recorded. Stripe's retries buy time, so this is urgent, not instant-catastrophic.
3. **`stripe_webhook_signature_failures_total` > 10 in 5 minutes** — page. Either the secret is wrong
   after a rotation (total outage of the endpoint, masked by 4xx responses that the availability SLI
   counts as fine) or someone is probing.
4. **p95 handler latency > 500 ms for 10 minutes** — ticket.
5. **Zero events received for 60 minutes during business hours** — ticket. A dead webhook is silent by
   nature; absence of traffic is the only symptom.

**Dashboard panels**: event volume by type (stacked), outcome split as a percentage over time (makes the
applied/ignored ratio impossible to miss), p50/p95/p99 handler latency, signature failure rate, event lag
distribution, and a table of the most recent failed `event_id`s for hand-off into a trace lookup.

**Also for DevOps**: `STRIPE_WEBHOOK_SECRET` must come from the secrets vault, and the rotation procedure
needs a runbook entry — alert 3 above exists precisely because a botched rotation silently breaks this
endpoint while every availability dashboard stays green.
