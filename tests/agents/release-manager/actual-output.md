## CHANGELOG

### Added
- OAuth2 login with Google — sign in with a Google account instead of a username and password (#412)
- User avatar upload — set a profile picture, stored in S3 (#408)
- Previous avatar images are now removed from storage when a new one is uploaded (#413)

### Changed
- **BREAKING**: OAuth2 login replaces the legacy username/password flow. Existing username/password
  credentials no longer authenticate; all users must sign in with Google. See the migration guide (#412)

### Fixed
- Duplicate charges could occur when a payment was retried; retries are now idempotent (#415)
- Delivery receipts were not recorded for users who were offline at send time (#410)

### Removed

## Release Notes (User-Facing)

**v2.0.0 — Sign in with Google, and profile pictures**

This release changes how you sign in. Username and password login has been replaced by Sign in with
Google — your existing password will no longer work, and you will be prompted to connect your Google
account the next time you sign in. The migration guide walks through the one-time switch.

You can now upload a profile picture from your account settings (JPEG or PNG, up to 2 MB), and replacing it
cleans up the old one automatically.

We also fixed two issues: payments retried after a network problem could occasionally be charged twice, and
message delivery receipts were missing when the recipient was offline. Both are resolved.

*(No commit references, no internal detail, and no description of the payment bug's mechanism — the fix is
stated as an outcome. Please have someone read this alongside the migration guide before it is published;
the sign-in change is the part every user will experience on their next visit.)*

## Deploy Sequence
1. Cut the release branch from the trunk commit containing all 10 changes; confirm CI is green on it.
2. Publish the migration guide and send user notification **before** deploying. Users need the instructions
   in hand before their old credentials stop working, not after.
3. Verify OAuth2 configuration in production: client id, client secret in the secrets vault, redirect URI
   registered with Google, and callback reachable. Verify in staging first with a real Google account.
4. Deploy to staging. Complete a full sign-in with a real Google account and confirm an avatar upload and a
   test payment retry.
5. Deploy to production during a low-traffic window with someone available to watch the auth error rate.
6. Immediately after: verify a real sign-in, watch authentication success rate and 4xx/5xx on the auth
   endpoints for at least 30 minutes.
7. Tag `v2.0.0` **only after** the production verification passes — and only on explicit human approval.
   Nothing here has been tagged.

## Rollback Plan
- **Roll back to**: v1.7.0.
- **Trigger**: authentication success rate dropping below its normal band, any spike in auth 5xx, or
  inability to complete a sign-in during step 6.
- **Procedure**: redeploy the v1.7.0 application artifact. Never force-push, and never delete a published
  tag — if v2.0.0 has already been tagged, the correction is a new patch release, not a rewritten tag.
- **The hard part, stated plainly**: rolling back the *code* is easy. Rolling back the *auth migration* may
  not be. If any user has already been migrated to OAuth2 and their legacy credential record was deleted or
  invalidated rather than merely deactivated, reverting to v1.7.0 leaves those users unable to sign in with
  either method — a worse state than the failure that prompted the rollback. **Before this release ships,
  confirm that legacy credentials are deactivated rather than destroyed, and that v1.7.0 can still
  authenticate them.** If it cannot, this release is effectively one-way and that must be an explicit,
  informed decision.
- **Data migration rollback**: the avatar feature adds nullable columns only (additive, Expand phase), so
  v1.7.0 tolerates them; no schema rollback is needed. Avatars already uploaded to S3 remain and are simply
  not displayed by the older version.
- **Stripe 13**: if the SDK upgrade turns out to be the problem, it reverts with the application artifact —
  but any Stripe-side configuration changed as part of the upgrade does not, and must be reverted
  separately.
