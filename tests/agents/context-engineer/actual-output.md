# Context Manifest: Add Rate Limiting to the Public API

## 1. Scope and Boundaries
- **Target Component**: public API middleware chain (`/api/v1/*`) and the Redis abstraction it will use for
  counter storage.
- **Relevant Layers**: Interface Adapters (middleware, HTTP concerns) and Frameworks & Drivers (the Redis
  client). **Explicitly not the domain layer** — rate limiting is a transport-level cross-cutting concern
  and has no business in entities or use cases. Any pin that pulls a use case or entity into scope is
  wrong for this task, and that judgment is what most of section 6 is enforcing.
- **Bounded Context**: API Gateway. The task touches Identity & Access only at the seam where the
  authenticated principal is read to key the limiter — it does not change authentication itself, and no
  Identity & Access internals need to be open.

## 2. Pinpoint Files (To Keep Open)

- [auth.middleware.ts](file:///src/api/middleware/auth.middleware.ts) — **implementation** — the task names
  this as "likely the right insertion point", and it is: the limiter must run *after* authentication
  (per-user limits need a resolved user id) and *before* the route handler. What is actually needed from
  this file is narrow — the middleware signature, the shape of the request object after auth attaches the
  principal, and the ordering of `next()` — not the authentication logic itself. **Pin the signature and
  the request-augmentation type only**; if the file is long, the relevant window is the exported middleware
  function and its type declarations. *Existence not verified in this run.*

- [redis-client.ts](file:///src/cache/redis-client.ts) — **interface** — the existing Redis abstraction.
  This is the highest-value pin in the manifest: whether the sliding-window counter can be implemented at
  all without new infrastructure depends entirely on what this abstraction already exposes. Specifically
  needed: does it expose `EVAL`/`EVALSHA` for a Lua script, or pipelining/`MULTI`, or only simple
  get/set? A sliding-window counter needs an atomic read-modify-write; if this client only offers
  get/set, the naive implementation has a race that lets bursts through under concurrency, and the task
  gains a dependency the requester has not budgeted for. **Pin the full public interface**;
  the connection-management internals are not needed. *Existence not verified in this run.*

- [ADR-007](file:///docs/adrs/ADR-007-redis-usage.md) — **decision record** — the task names it as covering
  "the Redis usage decision". Read for constraints on what Redis may be used for (cache-only vs. durable
  state?), eviction policy, and whether a shared or dedicated instance is expected. This matters concretely:
  if the Redis instance is configured with an LRU eviction policy for caching, rate-limit counters can be
  evicted under memory pressure and the limiter silently stops limiting. That is a real failure mode this
  ADR may already rule in or out. *Existence not verified in this run.*

- [rate-limiting notes from the auth overhaul](file:///docs/features/auth-overhaul/) — **prior delivery** —
  the task says this "may have relevant rate-limiting ADR notes". Pin only the specific artifact that
  mentions rate limiting (likely `analysis.md` or `architecture-notes.md`), not the whole delivery
  directory. See section 5. *Existence not verified in this run.*

- **Not yet identifiable but required**: wherever the `/api/v1/` middleware chain is *assembled* (an
  `app.ts`, `router.ts`, or route-registration module). The insertion point matters as much as the
  middleware itself, and this file is not named in the task. **First action for the next agent**: locate it
  with Glob before writing code — inserting the limiter in the wrong position (before auth) silently
  changes the limit from per-user to per-connection.

Deliberately **not** pinned: `.env`/config files (the two knobs, limit and window, are known from the task
text — 100 req/min), individual route handlers (the limiter is chain-level and route-agnostic), and any
test files (no existing rate-limit tests can exist yet).

## 6. Prune Recommendations (To Close)
- [ ] Any domain entity or use-case file — rate limiting is transport-level. If a `User` entity is open,
      close it; the limiter needs a user *id*, which arrives on the request, not the aggregate.
- [ ] The full `docs/features/auth-overhaul/` directory — pin the one artifact mentioning rate limiting;
      the implementation notes, QA report, and docs report from that delivery are noise here.
- [ ] Individual `/api/v1/` route handlers — the middleware applies to all of them and reading any
      particular one biases the design toward that route's shape.
- [ ] Redis client *internals* (connection pooling, reconnect logic) — the public interface is what
      matters; the internals are the adapter's business.
- [ ] The rest of `auth.middleware.ts` beyond its signature and request-augmentation type — the
      authentication mechanism is not changing, and reading it invites scope creep into auth.
- [ ] Any frontend or client-SDK code — `Retry-After` handling on the client is a separate task and
      pulling it in now doubles the surface for no benefit.

**One open question for the next agent, flagged here because it determines whether this task is small or

or accepting a race under burst load — and that is a design decision, not an implementation detail.
