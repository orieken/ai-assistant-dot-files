# Visual QA Report: Dashboard Redesign

## Summary

**FAIL**

- Heatmap analysis: FAIL — Coverage Score: 87% (threshold: 80%) — the score passes, but one HIGH-severity
  cold spot on a primary action does not, and severity is not averaged away by coverage.
- Visual regression: FAIL — 0 diffs detected against existing baselines, but the mobile viewport has **no
  baseline at all** for the three new sparkline components, so the most likely place for this redesign to
  break is the one place nothing is watching.
- Overall verdict: the functional suite is green and the desktop visuals are clean, but a redesign that
  adds three chart components ships with zero mobile coverage of them and a primary export action that
  nobody clicked in seven days — both are gaps that a passing functional run cannot see.

## Visual Regression

Six baselines exist: three pre-existing (`dashboard-overview.png`, `dashboard-mobile.png`,
`card-empty-state.png`) and three added this sprint (`sparkline-revenue.png`, `sparkline-users.png`,
`sparkline-errors.png`). No diffs are reported against any of them.

The problem is not what failed; it is the shape of what exists. `dashboard-mobile.png` predates the
redesign's sparklines, and the three new sparkline baselines are **desktop-viewport only**. The QA report
says so explicitly: "Mobile layout (375px) has not been tested with new sparklines — no mobile baseline for
sparklines yet."

That combination is the worst case for visual regression: a sparkline is a fixed-aspect SVG chart in a card
that must reflow to a 375 px column. Overflow, clipped axis labels, and unreadable text at that width are
the canonical failure modes for exactly this component type, and none of them can be caught by a desktop
baseline. `dashboard-mobile.png` may also now be a **stale baseline** — if it was captured before the card
layout and palette changed and is still passing, either it was recaptured without review or it does not
cover the changed region. Worth confirming which, because a silently-recaptured baseline is worse than no
baseline: it looks like coverage.

## Heatmap Coverage

Source: `heatmap-data/dashboard-2026-07-28.json`, one file, a 7-day window, Saturday-ML instrumented.
The analyzer could not be run in this environment; the figures below are derived from the coverage the QA
report states rather than computed, and are marked as such.

- Coverage Score: 87% (threshold: 80%) — **above threshold**
- Hotspots identified: not computed (analyzer not run)
- Cold Spots identified: 1 confirmed by the QA report (the bottom-right 300×200 px region)
- Scenarios analyzed: 1 heatmap JSON file

Two caveats about that 87%, because a passing number is exactly where this report is most likely to be
misread:

1. **One JSON file, one day, one viewport.** A single capture cannot distinguish "this element is never
   used" from "this element was not used on 28 July". Seven days of click data in one snapshot is a
   reasonable signal, not a verdict — and there is no mobile heatmap at all, so mobile interaction coverage
   is genuinely 0%, not 87%.
2. **Coverage is an area measure and severity is not.** 87% of the surface being exercised says nothing
   about whether the missing 13% contains a decorative divider or the primary export action. Here it
   contains the latter. The threshold passing is not the finding; the cold spot is.

## Cold Spots

| Element | Selector | Severity | Notes |
|---|---|---|---|
| "Export CSV" button | `[data-testid="export-csv"]` (bottom-right, 300×200 px region) | **HIGH** | Zero clicks in a 7-day window. This is a primary data-export action on an analytics dashboard — a core journey, not decoration. |
| Bottom-right quadrant surround | region `(x: -300, y: -200)` from bottom-right | LOW | The remaining area of that quadrant appears to be layout whitespace around the button; no other interactable is reported there. |
| Entire mobile viewport | — | **HIGH (unmeasured)** | No mobile heatmap data exists, so mobile is not a cold spot so much as an unlit room. Reported separately from the 87% because it is absent data, not measured absence. |

**On the Export CSV cold spot — two very different explanations, and they need different fixes.** Zero
clicks in seven days means either (a) the automated suite never exercises it, which is a *test coverage*
gap, or (b) real users cannot find it in its new bottom-right position after the redesign, which is a
*design* problem the redesign introduced. The heatmap alone cannot distinguish these, and guessing wrong
wastes the finding. If this capture came from a CI run, it is (a) and the fix is a test. If it came from
production instrumentation, it is (b) and the fix belongs to design — bottom-right is the weakest position
on a left-to-right reading dashboard, and "we moved the export button during a redesign and usage went to
zero" is a regression even though every functional test passes. **Confirm the data source before acting.**

## Recommendations

- [ ] **Capture mobile (375 px) baselines for all three sparklines** — `sparkline-revenue`,
      `sparkline-users`, `sparkline-errors`. Highest priority: fixed-aspect charts in a narrow column are
      the most likely thing in this redesign to be visibly broken right now.
- [ ] **Recapture `dashboard-overview` at 375 px** post-redesign, and confirm whether the existing
      `dashboard-mobile.png` is current or stale. If it was auto-recaptured without human review, treat it
      as absent.
- [ ] **Determine whether the heatmap came from CI or production**, then either add a `@visual` scenario
      exercising Export CSV (CI case) or raise the placement with design (production case). Do not do both
      blindly — adding a test that clicks the button makes the cold spot disappear from the heatmap without
      fixing a discoverability problem, which is worse than leaving it visible.
- [ ] **Add a dark-mode / `prefers-color-scheme` baseline** for the dashboard if the app supports it. The
      redesign changed the palette; this is the change that breaks the other theme.
- [ ] **Enable heatmap instrumentation on the mobile viewport** so mobile coverage is measured rather than
      assumed.
- [ ] **Capture a card-empty-state baseline at mobile width** — the empty state exists for desktop only,
      and empty states reflow differently from populated ones.
- [ ] **Collect more than one heatmap window** before treating any cold spot as settled. One file is a
      signal; a trend across several is evidence.

## Notes for QA

- The functional suite reports 22/22 pass and "no regressions in existing flows". That is accurate and also
  cannot see any of the above: every finding here is either a viewport with no baseline or an element with
  no interaction, and neither shows up as a failing assertion.
- When you add the mobile sparkline scenarios, set the viewport explicitly to 375×812 and **reload after
  resizing** — chart libraries commonly size on mount, so a resize without a reload produces a baseline
  that looks right in CI and wrong on a real device.
- Sparklines are the classic source of flaky visual diffs: entry animations and any time-based or random
  data will produce a different image on every run. Disable animation and pin the fixture data before
  capturing, or these three baselines will be re-recorded weekly until someone deletes them in
  frustration.
- If the Export CSV heatmap gap turns out to be a test gap, the new scenario should exercise the whole
  export path (click → download begins), not just a click on the button. A click-only test satisfies the
  heatmap while leaving the export itself untested — coverage theater, and the heatmap would then report
  green on it forever.
