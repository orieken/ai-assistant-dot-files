### The Red-Green-Refactor sequence, in order

**Cycle 1 — the domain check exists (criterion 3)**

Red first. The failing test before any implementation:

```ts
/**
 * @issue PROJ-518
 * @ac AC3: uniqueness is enforced at the domain layer, not only by the database constraint
 */
it('rejects registration when an email is already registered', async () => {
  const existing = new FakeUserDirectory([userWith('taken@example.com')]);
  const result = await User.register({ email: 'taken@example.com', password: 'hunter2!' }, existing);

  expect(result.ok).toBe(false);
  expect(result.error).toBe('EMAIL_ALREADY_REGISTERED');
});
```

This fails to compile — `User.register` does not exist. That is the correct kind of Red for the first
cycle. Green is the smallest thing that passes:

```ts
static async register(input: RegistrationInput, directory: UserDirectory): Promise<RegistrationResult> {
  if (await directory.existsWithEmail(input.email)) {
    return { ok: false, error: 'EMAIL_ALREADY_REGISTERED' };
  }
  return { ok: true, user: new User(UserId.generate(), input.email) };
}
```

`UserDirectory` is a port the domain owns — an interface with one method. The domain layer depends on
nothing outer, and the test drives a fake, not a database. This is the design pressure the criterion is
really asking for: "enforce at the domain layer" is unsatisfiable if the entity can only answer the
question by talking to Postgres.

**Cycle 2 — the endpoint returns exactly the specified 409 (criterion 1)**

```ts
/**
 * @issue PROJ-518
 * @ac AC1: duplicate email returns 409 Conflict with { "error": "EMAIL_ALREADY_REGISTERED" }
 */
it('returns 409 Conflict with EMAIL_ALREADY_REGISTERED for a duplicate email', async ({ api }) => {
  await seedUser('taken@example.com');
  const response = await api.post('/auth/register', {
    data: { email: 'taken@example.com', password: 'hunter2!' },
  });

  expect(response).toHaveStatus(409);
  expect(await response.json()).toEqual({ error: 'EMAIL_ALREADY_REGISTERED' });
});
```

`toEqual`, not `toMatchObject` — the criterion specifies the exact body, and a permissive assertion would
pass while the response carried extra fields.

**Cycle 3 — the database constraint is a backstop, not the mechanism**

```ts
/**
 * @issue PROJ-518
 * @ac AC3 - the domain check runs before persistence, not as a caught constraint violation
 */
it('rejects a duplicate without attempting to persist', async () => {
  const repository = new RecordingUserRepository([userWith('taken@example.com')]);
  await User.register({ email: 'taken@example.com', password: 'hunter2!' }, repository);

  expect(repository.saveCallCount).toBe(0);
});
```

This is the test that makes criterion 3 mean something. Without it, an implementation that inserts, catches
the unique-constraint violation, and translates it to a 409 passes both earlier tests while doing exactly
what the criterion forbids.

**Cycle 4 — the race the domain check cannot close**

```ts
/**
 * @issue PROJ-518
 * @ac AC3 - concurrent registrations for the same email: one succeeds, one gets 409
 */
it('handles two concurrent registrations of the same email', async () => {
  const [first, second] = await Promise.all([
    register('race@example.com'),
    register('race@example.com'),
  ]);

  const statuses = [first.status(), second.status()].sort();
  expect(statuses).toEqual([201, 409]);
  expect(await countUsersWithEmail('race@example.com')).toBe(1);
});
```

Check-then-insert is a TOCTOU race: both requests can pass the domain check before either inserts. The
database UNIQUE constraint is what actually prevents the duplicate — so the adapter must catch that
violation and translate it into the *same* `EMAIL_ALREADY_REGISTERED` 409 the domain check produces. The
domain check is the mechanism for the expected case; the constraint is the backstop for the concurrent one.
Both are required, which is a nuance the criteria imply without stating.

**Cycle 5 — anti-enumeration (criterion 2), and the contradiction inside it**

```ts
/**
 * @issue PROJ-518
 * @ac AC2 - an unauthenticated caller cannot learn whether an email is registered
 */
it('does not reveal registration status to an unauthenticated caller', async ({ api }) => {
  await seedUser('taken@example.com');
  const taken = await api.post('/auth/register', { data: { email: 'taken@example.com', password: 'hunter2!' } });
  const fresh = await api.post('/auth/register', { data: { email: 'fresh@example.com', password: 'hunter2!' } });

  expect(taken.status()).toBe(fresh.status());
  expect(await taken.json()).toEqual(await fresh.json());
});

/**
 * @issue PROJ-518
 * @ac AC2 - response timing must not distinguish taken from free (timing attack)
 */
it('takes comparable time for taken and free email addresses', async () => {
  const takenSamples = await sampleLatency(() => register('taken@example.com'), 30);
  const freeSamples = await sampleLatency(() => registerUnique(), 30);

  expect(Math.abs(median(takenSamples) - median(freeSamples))).toBeLessThan(TIMING_TOLERANCE_MS);
});
```

**These two tests contradict criterion 1, and the contradiction is real, not a misreading.** Criterion 1
demands a 409 with a body naming the reason. Criterion 2 demands that an unauthenticated caller cannot
learn whether an email is in the system. A 409 saying `EMAIL_ALREADY_REGISTERED` tells any anonymous caller
exactly that — it *is* the enumeration oracle. Both criteria cannot hold simultaneously for the same
caller. See Implementation Approach for how it was resolved and what still needs a human.

## Edge Cases Handled
- Duplicate email, expected case — domain check, 409, exact body.
- Duplicate email, concurrent case — TOCTOU race; database constraint as backstop, translated to the same
  409, exactly one row persisted.
- **Case sensitivity**: `Taken@Example.com` vs `taken@example.com`. Email local parts are technically
  case-sensitive per RFC, but no real provider treats them so, and users do not expect them to be. Both are
  treated as the same address, normalized to lower case at the domain boundary before comparison **and
  before storage** — normalizing only for comparison lets a differently-cased duplicate slip past the
  database constraint, which would defeat cycle 4's backstop.
- **Leading/trailing whitespace**: trimmed before normalization. `" taken@example.com"` must not register
  as a distinct account.
- **Unicode / homograph addresses**: normalized with NFC before comparison. Deliberately *not* attempting
  homograph-confusable detection — that is a separate security feature, and doing it partially is worse
  than not doing it. Flagged rather than half-built.
- **Empty and malformed email**: rejected at validation with 422, before the uniqueness check runs. A
  malformed address must not produce a 409, or 409 becomes a validity oracle as well.
- **Very long local part** (> 320 characters total): rejected at validation, so no unbounded string ever
  reaches the directory lookup.
- **Registration while a soft-deleted user holds the address**: **not handled — flagged.** Whether a
  deleted account's email is reusable is a product decision, not one I should make silently. The current
  behavior falls out of whatever the directory query does with soft-deleted rows, which is exactly the kind
  of accidental answer that becomes permanent.

## Implementation Approach

**Layering.** `User.register` is a static factory on the domain entity taking a `UserDirectory` port —
one method, `existsWithEmail(email: NormalizedEmail): Promise<boolean>`, defined in the domain and
implemented in the adapter. The domain imports nothing outward. This is what let the domain-layer criterion
be tested at all: cycles 1-4 run entirely against fakes, in milliseconds, with no database.

**`NormalizedEmail` value object.** Trimming, lower-casing, and NFC normalization happen once, in a type
that cannot be constructed in an un-normalized state. Two of the edge cases above are impossible by
construction rather than by remembering to call a helper at each call site — the difference between a rule
and a habit.

**Uniqueness is enforced twice, on purpose.** The domain check handles the expected case and produces the
specified error. The database UNIQUE constraint handles the concurrent case, and the adapter translates its
violation into the identical result. Neither alone is sufficient: the domain check has a TOCTOU window, and
the constraint alone violates criterion 3.

**The criterion 1 / criterion 2 conflict — how it was resolved, and what still needs you.**

The criteria as written cannot both be satisfied for the same caller. `POST /auth/register` is
unauthenticated by nature — that is what registration is — so criterion 2's "non-authenticated context" is
*every* caller of this endpoint, and criterion 1's explicit 409 hands each of them a definitive answer
about any address they care to try.

I made a decision rather than stopping, and I am documenting it as the rules require:

**Implemented**: criterion 1 as specified — 409 with `{"error": "EMAIL_ALREADY_REGISTERED"}` — plus every
compensating control that makes it defensible without contradicting itself:
- Strict rate limiting on `POST /auth/register` per IP and per address, so enumeration is possible in
  principle but not at any useful scale.
- Constant-time-ish response paths: the free-email path performs equivalent work to the taken path, so
  timing does not leak what the status code already discloses.
- Ordering: validation (422) runs before the uniqueness check, so 409 never doubles as a validity oracle.

**Why that way round**: criterion 1 is precise and testable and names an exact contract that clients will
depend on. Criterion 2 is a principle. Silently returning a generic 202 to satisfy the principle would
break the stated contract and produce a materially worse registration UX — a user who has simply forgotten
they already have an account gets no explanation at all. Choosing the vague requirement over the precise
one is not a decision an agent should make alone.

**What I need from you**: confirm the trade-off. The genuinely enumeration-safe design is different in kind
— registration always returns 202 "check your email", and the difference between "welcome, confirm your
address" and "you already have an account, here's a reset link" is delivered *by email*, to the address in
question, so only its actual owner learns anything. That satisfies both criteria fully, and it is a
different feature involving email delivery and a confirmation flow. If that is what criterion 2 intends,
say so and the 409 contract in criterion 1 must be rewritten, not adjusted. Cycle 5's tests are written to
the current decision and will need replacing if this changes.

**Refactor step (green → clean).** After cycle 4, the duplicate-detection logic appeared in both the domain
path and the constraint-violation translation path. Applied **Extract Function** to a single
`duplicateEmailResult()` so both produce a byte-identical result — the divergence that would otherwise
develop between them is precisely what cycle 5's parity assertion exists to catch, and the deduplication
makes it structurally impossible instead.
