# DevOps Report: User Avatar Upload

## Files Created

- **`infra/modules/avatar-storage/main.tf`** — Terraform module for the avatar bucket. Creates the bucket
  with **all public access blocked** (not merely a private ACL — `aws_s3_bucket_public_access_block` with
  all four flags true, since ACLs alone are no longer the effective control on modern buckets),
  server-side encryption enabled, versioning off (avatars are replaceable; versioning would quietly
  double storage and defeat the deletion path), and the lifecycle rule below. Every resource carries the
  mandatory `environment`, `owner`, and `project` tags per `shared/rules/iac-conventions.md`.

  The lifecycle rule the docs report asks for, written against what it actually needs to do:
  ```hcl
  rule {
    id     = "expire-orphaned-avatars"
    status = "Enabled"
    filter { prefix = "avatars/" }
    noncurrent_version_expiration { noncurrent_days = 30 }
    abort_incomplete_multipart_upload { days_in_progress = 1 }
  }
  ```
  **Flagged for human decision, not silently resolved**: the docs report says "30-day lifecycle rule for
  `avatars/` prefix" without saying *what expires*. A naive `expiration { days = 30 }` on the prefix would
  **delete every user's current avatar after 30 days** — a data-loss bug wearing a cleanup rule's clothes.
  The rule above expires only non-current versions and aborted multipart uploads, which is almost certainly
  the intent, but it does not sweep the true orphans (objects whose key no longer appears in any `users`
  row), because S3 lifecycle cannot express "not referenced by a database row". Sweeping those needs a
  scheduled reconciliation job. See Manual Steps Required.

- **`infra/environments/production/avatar-storage.tf`** and the staging equivalent — module invocations
  supplying environment-specific bucket names and tags. Environment config stays out of the module, per the
  module layout in `iac-conventions.md`.

- **`infra/modules/avatar-storage/iam.tf`** — the service-role policy, scoped exactly as the docs report
  specifies and no wider:
  ```json
  {
    "Effect": "Allow",
    "Action": ["s3:PutObject", "s3:DeleteObject", "s3:GetObject"],
    "Resource": "arn:aws:s3:::${bucket}/avatars/*"
  }
  ```
  Note the resource is the `avatars/*` **object** path only. No `s3:ListBucket`, which would require the
  bucket ARN itself and is not needed by any code path in this feature — and which would also make avatar
  keys enumerable by anything holding the role.

## New Environment Variables Required

| Variable | Description | Example | Secret? |
|---|---|---|---|
| `AWS_S3_BUCKET` | Bucket holding avatar objects under the `avatars/` prefix | `acme-prod-user-assets` | No |
| `AWS_REGION` | AWS region for the S3 client | `us-east-1` | No |

**On the docs report's line "they need to be added as secrets"** — respectfully, no, and this is worth
correcting rather than copying forward. Neither variable is a credential: a bucket name and a region are
configuration, and storing them as secrets makes them invisible in logs and plan output for no security
benefit while making misconfiguration harder to debug. They belong in environment-scoped **variables**.

The actual credential question is separate and more important: the application must obtain AWS credentials
from its **IAM task/instance role**, not from `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` environment
variables. Long-lived access keys in CI or production configuration are what
`architecture-guardrails.md` #3 exists to prevent. If any long-lived key is currently in use for this
service, replacing it with a role is a prerequisite to this feature shipping, not a follow-up.

## Deployment Notes

**Order matters, and it is not the obvious order:**
1. Apply the Terraform (bucket + IAM policy) **first**. The application will fail its startup check without
   the bucket, and the role needs the policy attached before the first upload.
2. Apply the database migration (additive, safe ahead of the deploy).
3. Deploy the application with both environment variables set.
4. Verify with a single test upload in production before announcing the feature.

Reversing 1 and 3 produces the confusing failure mode where the app deploys green and every upload 500s.

**Rollback**: redeploy the previous application version. The migration is additive and needs no rollback —
the nullable columns are simply ignored. Objects already written to S3 remain; they are orphaned but
harmless, and the reconciliation job (below) will sweep them once it exists. **Do not** delete the bucket
as part of a rollback; if the feature is re-enabled, those avatars are still referenced by rows the
migration left in place.

**Approval gates that apply here and have not been satisfied**: `terraform apply` requires a reviewed plan
and is an approval gate (`iac-conventions.md`); the migration is gate #3; the deploy itself is gate #8. All
three are **Always Human** — nothing in this report has been executed.

**What to watch after deploy**: upload success rate, S3 4xx/5xx from the application's perspective, and
the avatar-object deletion failure counter the developer notes call for. That last one is the only signal
that storage is leaking; the feature looks perfectly healthy while it does.

## Manual Steps Required

- **Approve and run `terraform plan`/`apply` for the bucket and IAM policy** in staging, then production.
  Human gate; I have not run it.
- **Run the database migration** against each environment. Human gate.
- **Confirm the lifecycle rule's intent before applying it.** As written above it expires non-current
  versions, *not* current avatars. If someone intended a flat 30-day expiry on the `avatars/` prefix, that
  would delete live user avatars, and I have deliberately not written that. This needs a human answer.
- **Build the orphan reconciliation job** — S3 lifecycle cannot express "object not referenced by any
  `users.avatar_key`". A scheduled job comparing bucket keys against the column is the only way to sweep
  true orphans from failed deletes. Not in scope for this change; raising it because the docs report's
  lifecycle rule will otherwise be assumed to cover it, and it does not.
- **Verify the service role uses IAM role-based credentials, not static access keys.** If static keys are
  in play, rotate to a role before this ships.
- **Set the two variables in the GitHub `production` and `staging` environments** — environment
  variables, not repository-level, so a fork PR cannot reach them.
