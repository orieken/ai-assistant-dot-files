# Documentation Report: User Avatar Upload

## Files Updated

- **`README.md`** — new "Avatar Upload" subsection under the User Profile API reference. Documents
  `POST /users/:id/avatar`: accepted formats (JPEG, PNG), the 2 MB size limit, the `422` responses for
  oversize and unsupported format with their distinct reason codes, and the response shape containing the
  new avatar URL. Includes the note that a file of *exactly* 2 MB is accepted — the limit is inclusive, and
  "max 2 MB" reads ambiguously enough that an API consumer will guess wrong.

- **`CHANGELOG.md`** — entry under v1.8.0:
  > **Added** — Users can upload a profile avatar (JPEG or PNG, up to 2 MB). Avatars are stored in S3 and
  > served from the profile page. Requires the new `AWS_S3_BUCKET` and `AWS_REGION` environment variables;
  > deployments without them will fail at startup.

  The environment-variable clause is in the changelog deliberately, not just the runbook: this is the entry
  an operator reads when a deploy breaks, and a new required variable is the most likely reason it did.

- **`docs/api/storage-adapter.md`** — **new**. API documentation for the `StorageAdapter` interface, which
  the QA report flags as new and undocumented. Covers the three methods (`put`, `remove`,
  `publicUrlFor`), the contract each implementation must honor, and — the part that actually matters —
  *why the interface exists*:
  > `StorageAdapter` is the boundary that keeps the AWS SDK out of the application's inner layers. Only
  > `src/storage/s3-adapter.ts` may import `@aws-sdk/client-s3`. If you are adding a storage backend,
  > implement this interface; if you find yourself importing an SDK type anywhere above the adapter layer,
  > the boundary has already leaked and the dependency-direction check will fail the build.

  Also documents the deliberate omissions: there is no `exists()` and no presigned-URL method, because
  nothing needs them yet. This prevents the next contributor from assuming those were forgotten.

- **`docs/runbooks/avatar-storage.md`** — **new**, per the QA report's explicit request for a runbook setup
  section. Contains: required S3 bucket configuration (private ACL, no public read), the IAM permissions
  the service role needs, the two environment variables with example values, and a **"Known gap"** section
  recording that the 30-day lifecycle rule for the `avatars/` prefix is *recommended but not implemented*.
  That gap is documented as a gap rather than described in the present tense — writing it up as though it
  exists is how a recommendation quietly becomes a false belief about production.

- **`docs/api/users.md`** — the profile response schema gains the `avatarUrl` field, marked nullable
  (users who have never uploaded one have no avatar).

## Files Unchanged (and why)

- **`docs/adrs/`** — **no new ADR.** Using S3 behind an interface adapter applies the existing architectural
  decision about hiding external dependencies; it does not make a new one. An ADR recording "we followed
  the rule we already wrote down" adds noise to the decision log and makes the genuinely load-bearing ADRs
  harder to find. If the lifecycle policy or a CDN in front of the bucket is added later, *that* is a real
  decision with alternatives and consequences, and it earns its own ADR.

- **`docs/setup.md`** — unchanged for local development. The S3 adapter is behind an interface, so local
  work uses the existing filesystem-backed implementation and needs no AWS credentials. Cross-referenced
  from the runbook so nobody concludes they need an AWS account to run the app.

- **`docs/architecture.md`** — unchanged. This feature adds a component inside an existing layer; it does
  not change the layer diagram.

- **Inline code documentation** — no changes requested. The QA report notes 96%/88%/91% coverage on the
  three modules and does not flag anything as unclear, so adding explanatory comments over code that
  reviewers found readable would be noise. The one exception worth a docstring is the concurrent-upload
  behavior — see Notes for DevOps.

## Notes for DevOps

- **New environment variables to add to deployment runbooks and CI:**
  | Variable | Purpose | Example |
  |---|---|---|
  | `AWS_S3_BUCKET` | Bucket holding avatar objects | `acme-prod-user-assets` |
  | `AWS_REGION` | Region for the S3 client | `us-east-1` |

  Both are required in **CI and production**, per the QA report. Neither is secret — they are
  configuration, not credentials. AWS credentials themselves come from the instance/task role and must not
  be added as environment variables.

- **The 30-day S3 lifecycle rule for the `avatars/` prefix is documented as recommended and NOT
  implemented.** I have written it into the runbook as an open ops item rather than as an existing
  control, because the QA report is explicit that it is not in place. This is the one documentation
  decision in this feature with a real operational consequence: the old-key deletion path exists but is
  best-effort, so storage grows slowly and silently without the sweep. Please confirm whether it is being
  implemented now or tracked separately, and I will update the runbook to match reality either way.

- **Bucket must be created with a private ACL.** Avatars are served through the application's URL
  generation, not by public bucket access. A publicly readable bucket would work and would also make every
  avatar enumerable — worth stating explicitly in the runbook, which I have done.

- **Concurrent-upload behavior is worth an ops note**: QA confirmed the second concurrent upload from the
  same user waits for the first via an advisory lock. If lock contention ever shows up in database
  monitoring under the avatar path, that is expected behavior rather than a bug — I have recorded it in the
  runbook so an on-call engineer does not chase it.

- **Nothing in this feature requires a rollback procedure beyond the standard deploy rollback.** The
  migration is additive and nullable; older application code ignores the new columns safely.
