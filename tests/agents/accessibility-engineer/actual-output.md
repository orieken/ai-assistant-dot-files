# Accessibility & UX Report: UserSearchBar.vue

## Evaluation Summary
- **Semantic HTML**: **Fail** — the component is div-soup. A search control is a `<div>` wrapper around a
  bare `<input>` with no `<form>`, the submit control is a `<div>` containing an emoji, and the results
  list is a `<ul>` of clickable `<li>` elements. Three interactive controls, zero interactive elements.
- **Interactive Elements**: **Fail** — `<div class="icon" @click="onSubmit">` and
  `<li @click="selectUser(result)">` are click handlers on non-interactive elements. Neither is focusable,
  neither responds to Enter or Space, and neither is announced as actionable by a screen reader. This is
  the exact pattern banned by `CLAUDE.md`'s frontend rules and by `design-principles.md`.
- **ARIA & Labels**: **Fail** — the input has **no accessible name at all**: no `<label>`, no
  `aria-label`, no `aria-labelledby`. `placeholder="Search users..."` is not a label; it disappears the
  moment the user types, and support for exposing it as an accessible name is inconsistent. The results
  list is a live-updating combobox with no ARIA relationship to the input, and the error message is
  visually present but never announced.
- **Keyboard Navigation**: **Fail** — a keyboard user can reach the input (it is natively focusable) and
  submit with Enter, and then is stuck. The search icon cannot be reached. No result can be selected. The
  component's entire output is unreachable without a mouse.

**Combined severity**: this component is unusable by keyboard-only and screen-reader users. Not degraded —
unusable. Four of four dimensions fail.

## Findings & Fixes

### 1. Input has no accessible name — WCAG 4.1.2 (A), 3.3.2 (A) — **auto-fix**
`tests/agents/accessibility-engineer/input-component.vue` lines 4-10

`placeholder` is a hint, not a name. A screen reader announces this control as "edit, blank".

```vue
<label for="user-search-input" class="sr-only">Search users</label>
<input
  id="user-search-input"
  type="search"
  placeholder="Search users..."
  @input="onInput"
/>
```

`type="search"` rather than `type="text"` — it is semantically correct and gives mobile keyboards a search
action key. A visually-hidden `<label>` (`.sr-only`) is used rather than `aria-label` because a real label
element is also a click target that focuses the input, which `aria-label` is not.

### 2. `<div class="icon" @click>` is a button — WCAG 2.1.1 (A), 4.1.2 (A) — **auto-fix**
line 11

This is the single worst finding: the submit control cannot be focused, cannot be activated by keyboard,
and is announced (if at all) as an image of a magnifying glass with no role and no name.

```vue
<button type="submit" class="icon">
  <span aria-hidden="true">🔍</span>
  <span class="sr-only">Search</span>
</button>
```

A native `<button>` brings focusability, Enter/Space activation, the correct role, and focus styling for
free. The emoji is hidden from assistive technology (`aria-hidden`) because "left-pointing magnifying
glass" is not a useful announcement, and the real name is supplied as visually-hidden text. Do **not**
"fix" this by adding `role="button"` and `tabindex="0"` to the div — that reimplements, badly, what the
native element already does, and it is the ARIA misuse `CLAUDE.md` calls out specifically.

### 3. Clickable `<li>` results are unreachable — WCAG 2.1.1 (A) — **needs a decision, not a one-line fix**
lines 15-19

Each result is a `<li>` with a click handler: not focusable, not activatable, not announced as selectable.
The minimal correct fix is to make each result a real button:

```vue
<li v-for="result in results" :key="result.id">
  <button type="button" @click="selectUser(result)">{{ result.name }}</button>
</li>
```

Note `:key="result.id"` — the original `v-for` has no `key`, which is a Vue correctness bug independent of
accessibility, and it causes assistive technology to receive incoherent DOM updates as results change.

**Flagged rather than silently applied**: this is a search field with a live-updating result list, which
is a **combobox** pattern, and buttons-in-a-list is only the floor. The complete pattern needs
`role="combobox"` with `aria-expanded` and `aria-controls` on the input, `role="listbox"`/`role="option"`
on the list, arrow-key navigation with `aria-activedescendant`, and Escape to dismiss. That is a
meaningful behavioral change and a design decision, not an auto-fix — a human should confirm the
interaction model before it is built.

### 4. Error message is never announced — WCAG 4.1.3 (AA), 3.3.1 (A) — **auto-fix**
lines 12-14

`v-if="errorMsg"` inserts the error into the DOM with no live region, so a screen-reader user gets no
notification. Compounding it, the error is conveyed by `color: red` alone, which fails 1.4.1 (Use of
Color) and is invisible to users with red-green color vision deficiency.

```vue
<div v-if="errorMsg" class="error" role="alert" aria-live="assertive">
  <span aria-hidden="true">⚠️</span> {{ errorMsg }}
</div>
```

`role="alert"` (implicitly `aria-live="assertive"`) is correct for errors specifically. Move the styling to
a CSS class that pairs color with the icon and a non-color cue — never inline `color: red` as the sole
signal.

### 5. Result count is not announced — WCAG 4.1.3 (AA) — **auto-fix**
lines 15-19

Results appear as the user types with no announcement, so a screen-reader user has no idea anything
happened.

```vue
<div aria-live="polite" class="sr-only">
  {{ results.length }} {{ results.length === 1 ? 'result' : 'results' }} found
</div>
```

`polite` here, not `assertive` — search results should not interrupt the user mid-typing, unlike an error.

### 6. Text contrast fails — WCAG 1.4.3 (AA) — **auto-fix**
line 9: `style="color: #999; background: #eee;"`

`#999` on `#eee` is a contrast ratio of approximately **2.0:1**. The AA minimum for body text is **4.5:1**;
this is less than half. It fails for everyone in bright light, not only users with low vision.

Remove the inline style and use a token meeting AA: `#595959` on `#eee` reaches ~4.6:1, and `#767676` on
white is the usual safe minimum. Verify the placeholder color too — placeholder text is frequently styled
even lighter than the input text and is subject to the same requirement.

### 7. No form element — WCAG 1.3.1 (A) — **auto-fix**
lines 3-11

Wrapping the input and the submit button in a `<form>` (with `@submit.prevent="onSubmit"`) gives implicit
submit-on-Enter, groups the controls semantically, and lets the `type="submit"` button in finding 2 work
without a click handler at all. The current `@keydown.enter` on the input is a hand-rolled substitute for
behavior the platform provides.

### 8. `onSubmit` emits an empty string — **not an accessibility finding; flagged for the developer**
lines 33-35

`function onSubmit() { emit('search', ''); }` emits an empty query, discarding whatever the user typed.
Clicking the search icon appears to clear the search rather than run it. Outside this agent's remit, but
it will read as an accessibility bug in testing ("the search button doesn't work"), so it is recorded here
so it is not misattributed.

### Fixes NOT applied and why
All of the above are specified but **unapplied** — the file is an evaluation fixture whose flaws are the
point of its existence; editing it would break the test it supports. In a normal run, findings 1, 2, 4, 5,
6, and 7 would be applied directly with `Edit` and reported as fixed; finding 3 would be raised for a
human decision on the combobox pattern; finding 8 would be handed to the developer.

## Notes for QA

**Keyboard-only** (unplug the mouse — the point is to be unable to cheat):
- Tab to the search field. Confirm it has a visible focus indicator and that a screen reader announces it
  as "Search users, search field", not "edit, blank".
- Tab again. Focus must land on the search button. In the current code it does not — this is the fastest
  way to confirm finding 2 is fixed.
- Press Enter in the field and confirm the search runs with the typed value, not an empty string
  (finding 8).
- Tab into the results and activate one with **both** Enter and Space. Both must work; a `<div>` with a
  click handler answers to neither.
- If the combobox pattern from finding 3 is implemented: arrow keys move between options, Enter selects,
  Escape closes and returns focus to the input.

**Screen reader** (VoiceOver + Safari and NVDA + Firefox at minimum — their live-region behavior differs
in ways that matter here):
- The input is announced with a name and a role on focus.
- Typing a query produces a result-count announcement without interrupting typing.
- An error is announced immediately when it appears.
- Each result is announced as an actionable control, not as static list text.

**Visual / other**:
- Run an automated contrast check on the input text, the placeholder, and the error text. Assert ≥ 4.5:1.
- Set the OS to grayscale and confirm the error state is still identifiable — that verifies finding 4's
  non-color cue rather than trusting it.
- Zoom to 200% and confirm no content is clipped or overlapped.
- `await page.accessibility.snapshot()` in the Playwright spec, asserting the input node has a non-empty
  `name` and the submit control has `role: button`. That single assertion catches regressions on the two
  most severe findings automatically, which is worth more than any of the manual steps above.
