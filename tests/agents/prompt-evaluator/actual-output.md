# Prompt Evaluation Report: data-migrator (draft)

## Summary
- Total Prompts Evaluated: **1**
- Secret Leaks Found: **1**
- Inline Example Violations: **1**

**Verdict: BLOCKER.** This prompt must not be committed as written. One hardcoded credential, one
unreachable external URL presented as an authoritative source, one example coupled to a decision record the
agent will not have, and inconsistent instruction voice. The underlying agent concept is sound — a
migration specialist enforcing Expand/Contract is a legitimate role, and the two constraints at the end are
correctly stated — but four distinct authoring-hygiene defects sit on top of it.

## Findings

### Critical Secret Leaks

- [`shared/agents/data-migrator.md`]: Responsibility 3 contains a literal database connection string with
  embedded credentials:

  > `postgres://admin:hunter2@localhost:5432/myapp_dev`

  **BLOCKER.** `architecture-guardrails.md` #3 names connection strings explicitly alongside API keys and
  passwords. Four things are wrong here, and only the first is obvious:

  1. **A username and password are written in plaintext** into a file destined for version control, where
     they are permanent regardless of later edits.
  2. **`localhost` makes it look harmless, and that is the trap.** The credential pair `admin`/`hunter2` is
     the reusable artifact, not the host. Developers copy the whole string; the password travels with it
     into `.env` files, shell history, and eventually a non-local connection.
  3. **It instructs the agent to connect to a database at all.** "For local testing, connect to..." tells
     the agent to open a database connection as a matter of course. A migration agent reaching a live
     database is an approval-gated action (`approval-gates.md` #3, Always Human) — this line invites the
     agent to route around a gate that exists specifically for this class of operation. That is a worse
     defect than the leaked password.
  4. **`hunter2` reads as a joke placeholder**, which is exactly why it will not be treated as a secret by
     reviewers and will survive into the committed file.

  **Required**: delete the connection string entirely. If the agent genuinely needs database access, it
  reads a connection URL from an environment variable — and the instruction should say so, and should say
  that connecting requires human approval.

### Fabricated / Unverifiable External URL

- [`shared/agents/data-migrator.md`]: The Constraints section ends with:

  > `Always read https://company-internal.example.com/db-standards for the latest naming conventions`

  **BLOCKER.** `example.com` is an IANA-reserved domain that exists precisely so it can never resolve to
  real content. `company-internal.example.com` is therefore, with certainty and without needing to fetch it,
  a **fabricated URL** — a placeholder left in a prompt as though it were a real source. (It was not
  fetched; this agent makes no external calls, and none is needed to reach this conclusion.)

  The consequence is worse than a dead link. The word **"Always"** makes this a standing instruction to
  consult an authority that does not exist. Every run either fails on it, silently skips it, or — the worst
  case — the model proceeds as if it had read the standards and invents naming conventions that sound
  plausible and match nothing. A confidently fabricated convention is far more damaging than a missing one.

  Additionally, even if a real internal URL replaced it: an agent instructed to fetch an internal
  documentation site on every run has an external dependency with no timeout and no failure path stated, and
  its content becomes an unvalidated input channel. Naming conventions belong in `DOMAIN_DICTIONARY.md` or a
  rules file inside the repository, where they are versioned, reviewable, and inside the trust boundary.

### Inline Template Example Violations

- [`shared/agents/data-migrator.md`]: The "Example Output" section inlines a SQL snippet coupled to a
  specific decision record:

  > ```sql
  > -- ADR-011 required this exact column addition
  > ALTER TABLE users ADD COLUMN tenant_id UUID NOT NULL DEFAULT gen_random_uuid();
  > ```

  Two coupling problems and one correctness problem:

  1. **Coupled to ADR-011**, described as "a real example from a prior migration". Any project installing
     this agent has no ADR-011, or has an unrelated one. The comment asserts a requirement the agent cannot
     verify and the reader cannot check, and it teaches the agent to cite decision records by number as
     justification — a habit that produces confident, unfounded citations elsewhere.
  2. **Coupled to a specific schema** (`users`, `tenant_id`). An agent prompt's example should demonstrate
     the *shape* of correct output, not one project's table. Where a template exists, the prompt should
     reference `shared/templates/data-engineering-notes.template.md` rather than inline an example at all —
     that is the framework's established pattern and this prompt does not follow it.
  3. **The example is a poor demonstration of the very rule the prompt enforces.** It adds a `NOT NULL`
     column with `DEFAULT gen_random_uuid()`, which technically satisfies "NOT NULL needs a DEFAULT" while
     assigning every existing row a **random, meaningless tenant id** — silently corrupting tenancy for all
     historical data in a way no constraint will ever catch. A prompt whose one worked example models a
     subtly destructive migration is teaching the wrong lesson under the banner of the right rule. This is
     the most damaging finding in the section, and it is invisible unless the example is read as SQL rather
     than as illustration.

### Inconsistent Instruction Voice

- [`shared/agents/data-migrator.md`]: The prompt mixes three voices, which weakens the constraints that
  matter most:
  - **Numbered procedural imperatives** in Responsibilities ("Review the migration plan…", "Produce
    `data-engineering-notes.md`…") — appropriate.
  - **Emphatic ALWAYS/NEVER** in Constraints ("ALWAYS use the Expand/Contract pattern", "NEVER use `DROP` in
    phase 1") — the framework's convention for hard constraints, and correct here.
  - **A third, softer register mid-list**: Responsibility 2 states "Enforce the Expand/Contract pattern
    (never `DROP COLUMN` in phase 1)" as a lowercase parenthetical, while Constraints restates the same rule
    in caps. **The same rule appears twice at two different strengths**, which is the specific problem:
    duplicated constraints drift when one copy is edited, and a rule stated once softly and once loudly
    signals that emphasis is decorative rather than meaningful.

  Recommended: state each hard constraint exactly once, in the Constraints section, in the ALWAYS/NEVER
  form. Remove the parenthetical from Responsibility 2.

### What is Correct

- Reading `analysis.md` from `.claude/feature-workspace/` and writing `data-engineering-notes.md` there

- The two Constraints are the right constraints, correctly phrased.
