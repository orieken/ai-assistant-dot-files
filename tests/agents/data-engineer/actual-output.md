# Data Engineering Notes: Multi-Tenant Schema Migration

**The proposed migration must not be run.** As written it is a single statement that violates two hard
constraints and will fail outright on the stated data:

```sql
ALTER TABLE orders ADD COLUMN tenant_id UUID NOT NULL REFERENCES tenants(id);
```

Three separate problems, any one of which is disqualifying:

1. **`NOT NULL` with no `DEFAULT`** — banned by `architecture-guardrails.md` #2. On a table with 8 million
   existing rows this does not merely violate a rule, it **cannot succeed**: Postgres must give every
   existing row a value, and there is none. The statement errors out and the transaction rolls back. The
   rollout plan meanwhile says "existing rows will have `tenant_id = NULL` until a backfill job runs" —
   that is self-contradictory with `NOT NULL`, and the contradiction is the tell that the plan and the DDL
   were written separately and never reconciled.
2. **The lock.** The analysis estimates a 45-second table lock and treats it as a cost to accept. Adding a
   nullable column without a default is metadata-only in modern Postgres and takes milliseconds — but
   `REFERENCES tenants(id)` adds a foreign key, which takes an `ACCESS EXCLUSIVE` lock and validates all 8
   million rows. For 45 seconds, **every read and write to `orders` blocks**, including queries already
   holding transactions. On a production orders table that is an outage, and it will not be reported as
   "the migration was slow" — it will be reported as the checkout being down.
3. **Single-phase destructive-in-effect change.** Making the column mandatory in the same release as the
   code that starts populating it means there is no window where old and new code can both run. That
   forecloses a rolling deploy and any rollback.

The rest of this document is the four-phase version that reaches the same end state with no blocking lock
and a safe rollback at every step.

## Schema Changes

- **`orders`**
  - `ADDED tenant_id (UUID)` — **nullable initially**, no default, no inline foreign key. Nullable is not a
    compromise here; it is the mechanism that makes the change non-blocking, and it is temporary.
  - `ADDED CONSTRAINT orders_tenant_id_fkey FOREIGN KEY (tenant_id) REFERENCES tenants(id)` — added
    separately as `NOT VALID`, then validated in its own transaction (Phase 1b).
  - `ADDED CONSTRAINT orders_tenant_id_not_null CHECK (tenant_id IS NOT NULL) NOT VALID` — the check
    constraint stands in for `SET NOT NULL` because it can be validated without an `ACCESS EXCLUSIVE` lock
    (Phase 3). On PostgreSQL 12+, a validated check of this exact form also lets `SET NOT NULL` be applied
    later without a full table scan.
  - `ADDED INDEX idx_orders_tenant_id ON orders (tenant_id)` — created `CONCURRENTLY`. **Not optional**:
    the analysis states every query against `orders` will filter by `tenant_id` from now on, so this index
    is on the hot path of the entire table's access pattern from the moment the code ships.

- **`tenants`** — unchanged. Assumed to exist and be populated; if it is not, that is a prerequisite, not
  part of this migration. **This must be confirmed before Phase 1** — the foreign key has nothing to point
  at otherwise.

## Migration Strategy

- **Phase**: **Expand** (Phases 1-3 here), with the Contract phase deliberately deferred to a later
  release.

- **Details**:

  **Phase 1 — Expand (safe, additive, deployable immediately)**
  ```sql
  -- 1a. Metadata-only. Milliseconds, no table rewrite, no blocking lock.
  ALTER TABLE orders ADD COLUMN tenant_id UUID;

  -- 1b. NOT VALID skips the scan; the ACCESS EXCLUSIVE lock is held only for the catalog update.
  ALTER TABLE orders
    ADD CONSTRAINT orders_tenant_id_fkey
    FOREIGN KEY (tenant_id) REFERENCES tenants(id) NOT VALID;

  -- 1c. Validation takes only a SHARE UPDATE EXCLUSIVE lock — reads and writes continue.
  ALTER TABLE orders VALIDATE CONSTRAINT orders_tenant_id_fkey;

  -- 1d. Outside a transaction block. Does not block writes.
  CREATE INDEX CONCURRENTLY idx_orders_tenant_id ON orders (tenant_id);
  ```
  After Phase 1 the column exists and is empty. Existing code is unaffected — it does not know the column
  is there. **This is the rollback point**: everything to here is reversible by dropping a column nothing
  reads.

  **Phase 2 — Application dual-write, then backfill (the part the original plan got backwards)**

  The proposed rollout deploys the migration and *then* the code that populates `tenant_id`. Between those
  two events every new row is written with a NULL tenant — so the backfill has to chase a moving target,
  and it can never converge while writes continue. The order must be:

  1. **Deploy application code that writes `tenant_id` on every insert and update** to `orders`. New rows
     are correct from this moment. The code must still tolerate reading NULL for old rows.
  2. **Only then backfill**, in bounded batches, oldest first:
     ```sql
     UPDATE orders SET tenant_id = <resolved>
      WHERE tenant_id IS NULL AND id IN (
        SELECT id FROM orders WHERE tenant_id IS NULL ORDER BY id LIMIT 5000
      );
     ```
     Batches of ~5,000 with a short pause between them, each in its own transaction. 8 million rows is
     roughly 1,600 batches; expect tens of minutes to a few hours depending on how `tenant_id` is resolved
     and on replica lag. **Never a single `UPDATE` over 8 million rows** — it holds row locks for the
     duration, bloats the table, and cannot be interrupted safely.
  3. **Monitor replication lag between batches** and back off if it grows. This is the most common way a
     technically-correct backfill causes a production incident.
  4. Confirm convergence: `SELECT count(*) FROM orders WHERE tenant_id IS NULL` reaches zero **and stays
     there** across two consecutive checks.

  **How is `tenant_id` resolved for existing rows?** — **This is an open question the analysis does not
  answer, and it blocks Phase 2.** Eight million historical orders must each be attributed to a tenant, and
  nothing in the analysis says from what: a customer→tenant mapping, an account column already on `orders`,
  or a per-row lookup. If any historical order cannot be attributed, the plan needs an explicit answer for
  it (a designated legacy tenant, or exclusion from the constraint). Backfilling the wrong tenant is a
  **data-isolation breach in a multi-tenancy feature** — the precise failure this whole change exists to
  prevent — so this must be answered by a human before Phase 2 runs, not inferred.

  **Phase 3 — Enforce (still Expand; safe, non-blocking)**
  ```sql
  -- NOT VALID first: catalog-only, so no scan while holding the strong lock.
  ALTER TABLE orders
    ADD CONSTRAINT orders_tenant_id_not_null CHECK (tenant_id IS NOT NULL) NOT VALID;

  -- Validation scans under SHARE UPDATE EXCLUSIVE — reads and writes continue throughout.
  ALTER TABLE orders VALIDATE CONSTRAINT orders_tenant_id_not_null;
  ```
  Run **only after** Phase 2 confirms zero NULLs. If any remain, validation fails and rolls back — which is
  the desired behavior, not a setback.

  Optionally, once the check is validated, `ALTER TABLE orders ALTER COLUMN tenant_id SET NOT NULL` becomes
  cheap on PG 12+ (the validated check proves the property, so no full scan). The check constraint alone is
  sufficient enforcement; converting is tidiness, not necessity.

  **Phase 4 — Contract (a LATER release; requires its own approval gate)**
  Dropping the redundant check after `SET NOT NULL`, or removing any transitional column, is the only
  destructive work here and belongs in a separate release, behind
  `approval-gates.md` #4 ("confirm contract phase"). Nothing in this change requires a Contract phase to
  deliver the feature — worth stating, because the temptation is to bundle it.

  **Lock summary** — no step in any phase takes an `ACCESS EXCLUSIVE` lock for longer than a catalog
  update:
  | Step | Lock | Duration |
  |---|---|---|
  | 1a add nullable column | ACCESS EXCLUSIVE | milliseconds (metadata only) |
  | 1b add FK `NOT VALID` | ACCESS EXCLUSIVE | milliseconds (no scan) |
  | 1c validate FK | SHARE UPDATE EXCLUSIVE | minutes, non-blocking |
  | 1d `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCLUSIVE | minutes, non-blocking |
  | 2 backfill batches | row locks only | per batch |
  | 3 add + validate check | SHARE UPDATE EXCLUSIVE | minutes, non-blocking |

  Compare against the original single statement: 45 seconds of total table unavailability, and it fails
  anyway.

  Set `lock_timeout = '3s'` and `statement_timeout` on every DDL session. If a step cannot acquire its lock
  promptly it should fail fast and be retried, rather than queueing behind a long-running transaction and
  blocking every query that arrives after it — the lock-queue pile-up is what turns a fast DDL into an
  outage.

## Developer Handoff Notes

- **Deploy dual-write code before backfilling, not after.** This is the single most important ordering
  change from the proposed plan. Backfilling while new NULLs are still being written cannot converge.
- **Application code must tolerate `tenant_id IS NULL` throughout Phase 2.** Between Phase 1 and the end of
  the backfill, both shapes exist. Code that assumes the column is populated will fail on historical rows —
  and it will fail on the *oldest* rows, which are the least likely to be exercised in testing.
- **Every query against `orders` must filter by `tenant_id` once the feature is live** — that is the entire
  point of the change. Filtering must be enforced structurally (a repository-level scope, or Postgres
  row-level security), not by remembering to add a `WHERE` clause at each call site. A single forgotten
  filter is a cross-tenant data leak, and it will not be caught by any test that runs with one tenant's
  data.
- **Add `tenant_id` as the leading column of composite indexes on `orders`**, not a trailing one. If a
  query filters `tenant_id` and orders by `created_at`, the useful index is
  `(tenant_id, created_at DESC)`. The standalone index in Phase 1 is the minimum, not the finished access
  design — review the existing indexes on `orders` and expect several to need rebuilding with `tenant_id`
  first.
- **Watch for N+1 on the tenant relation.** Now that `orders` references `tenants`, any per-order tenant
  lookup in a loop is an N+1. Eager-load or DataLoader it (`architecture-guardrails.md` #6).
- **Answer the attribution question before writing the backfill script** — how a historical order maps to
  a tenant, and what happens to rows that map to none. Everything else here is mechanical; that one is a
  correctness decision with a data-isolation blast radius.
- **Rehearse on a production-sized copy.** The 45-second estimate in the analysis came from somewhere, and
  the phased plan's timings should come from a real rehearsal rather than from this document's estimates.
